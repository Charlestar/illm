# Policy-aware CPU profile: contract revision 2

This is a development runbook for `0.2.0.dev0`, not a published V0.2 release.
The human approval covers the specification and CPU implementation only. GPU
execution remains deferred, and the historical GPU budget is still unreconciled.
The [approved protocol](v0.2-numerical-policy-protocol.md), accepted
[SPEC-v3](../specs/versions/v0.2-stateful-streaming.md), and
[ADR-007](../adr/ADR-007-numerical-execution-policies.md) remain authoritative.

## What this iteration changes

The new sibling implementation uses qualification schema **3**, contract
revision **2**, explicit numerical policies, capture3/R0, MemoryPlan2, API
revision2 and generation-result JSON3. It does not reinterpret historical
schema2 profiles, captures, rollback-v1 evidence, or the frozen V0.1 reference.

`run_v02_policy_gate.py` describes fifteen ordered CPU phases:

1. Fresh locked offline environment bootstrap.
2. Approved input stage.
3. One complete quality/pytest/example execution, owned by the CPU stage.
4. Read-only verification of those three development stages.
5. Raw numerical collection from five isolated CPU workers.
6. Independent stdlib raw-byte recomputation.
7. Candidate full-recompute B and true-KV C CLI demonstrations, with seed7.
8. C capture replay and request inspection.
9. One hundred lifecycle cycles, eight finish/cancel races, and twelve faults.
10. Copied schema3/R0 reader proof, then a fresh isolated copied-reader check.
11. Cancellation learning assets, then exact regeneration verification.

The list groups related phases for reading; the machine contract contains all
fifteen individual commands. There is no second outer pytest/quality run hiding
behind the development driver. Controlled CPU faults are not actual GPU faults.

## Run only after freezing the source

Use a new environment name and a new output path for every attempt. The runner
refuses existing paths and never erases a previous failure. Ensure the pinned
CPU artifacts already exist in `.illm/cache/runtime`; this command is offline
and does not download dependencies. Raw tensors and comparison records occupy
substantial disk space, and sealing keeps a separate evidence copy.

From PowerShell on Windows:

```powershell
python scripts/run_v02_policy_gate.py `
  --profile v02-policy-profile-cpu-r1 `
  --profile-id state-machine-cpu-v1 `
  --output out/v02-policy-profile-cpu-r1
```

The initial Python is only the control plane. All post-bootstrap commands go
through `in_env.py` and the finalized manifest. Do not activate an unrelated
environment or reuse an old manifest after changing source, tests or docs.
The `clean-room-release-v1` profile uses the same CPU contract in an independent
fresh Linux CPU environment; copying a Windows profile is not that experiment.
The GPU profile name is registered but rejected before any subprocess, output
creation, model load or GPU initialization.

The final `qualification/` directory embeds the manifest, source/lock inventory,
approved protocol/input/receipt bytes, descriptors, all component evidence and
closed command transcripts. `policy-cpu-pytest-scratch/` is retained diagnostic
scratch, not evidence, and is not copied into the profile.

The quality component keeps the existing producer's wire format: sorted JSON
with spaces, followed by CRLF for a manifest-bound Windows CPU runtime or LF
for a manifest-bound Linux CPU runtime. Portable readers choose that exact
encoding from the producing toolchain, not the reading host. Other canonical
JSON artifacts retain their compact encoding. Raw quality stdout must still
match the quality file byte for byte; duplicate fields, nonfinite values,
unknown producer pairs and arbitrary whitespace remain invalid.

To read an existing profile with an installed current reader:

```powershell
python scripts/qualify_v02_policy.py --verify-existing PATH_TO_COPIED_QUALIFICATION
```

The reader uses embedded relative links and stdlib numerical recomputation; it
does not execute archived scripts or open historical author-machine paths.
Hash and transcript verification establish internal consistency, not a signature
proving an author's honesty. A standalone raw report and copied-capture proof
keep their literal `DEVELOPMENT_ONLY` labels even inside this CPU profile.

## Interpret the result correctly

| Field | Meaning |
|---|---|
| Profile `result=pass`, `scope=cpu-profile-only` | This source's complete CPU profile contract passed |
| `cpu_results` | Raw-derived tiny-FP32 results; all three CPU axes must pass |
| Three top-level result axes `incomplete` | The complete CPU/GPU protocol has not passed |
| `qualification_tier=unqualified` | No global release qualification |
| `global_qualification_granted=false`, `gpu_qualification_granted=false` | No implicit promotion or GPU result |
| Component/profile `COMPLETE` | That container was sealed; not a release announcement |

Tiny-FP32 legacy elementwise compatibility remains a hard gate. Only the
approved, fully measured low-precision legacy comparison may later be reported
as `fail` without replacing the new policy's independent hard gates. Missing
or incomplete measurements cannot be relabelled as such a completed failure.

## Rollback is a separate component

`rehearse_policy_rollback.py` / `stateful_policy_rollback.py` use the new
`illm-stateful-policy-rollback-v2` kind, schema2. They must prove actual C
completion, known fences, all eleven resource counters at zero, a closed Engine
rejecting admission, then a new Engine explicitly using **legacy+none=A**.
Candidate+none=B is not A. No accepted request changes policy in place.

The independent old runtime is installed offline from the frozen annotated
`v0.1.0` tag and locks. Its identity is `source-built-installed-runtime`, bound
to the immutable tag/commit, source, release bundle and new old-version
environment. The repository has no prebuilt V0.1 executable whose digest could
truthfully be reported. No new policy ID is retroactively assigned to V0.1.
Old-reader schema2/schema3 rejection and new-reader schema0/1/2/3 handling are
separate actual compatibility checks, not assertions inferred from a tag name.

This rehearsal is not an extra fake phase in the CPU profile and cannot grant
global or GPU qualification on its own. Public readers reject synthetic fixtures.
After the complete CPU gate, a separate new rehearsal output can be requested
through that same finalized interpreter (use an unused output name):

```powershell
python scripts/in_env.py `
  --manifest out/v02-policy-profile-cpu-r1/toolchain.json `
  --expected-manifest-digest-file out/v02-policy-profile-cpu-r1/toolchain.sha256 `
  -- python scripts/rehearse_policy_rollback.py `
  --v02-toolchain-manifest out/v02-policy-profile-cpu-r1/toolchain.json `
  --trusted-git-repository . --artifact-cache .illm/cache/runtime `
  --trigger-reason "CPU-only compatibility rehearsal; GPU deferred" `
  --output out/v02-policy-rollback-r1
```

This creates a fresh old-version environment under the rehearsal's explicitly
excluded `local-only/` build work. That directory is not portable evidence;
archive or retain it separately if needed. Do not point the rehearsal at a
user's active V0.1 environment.

## Remaining release work

The first policy-aware Windows/Linux attempts at `3a80d75` exposed a reader
bug: actual quality output uses spaced JSON and platform newlines, while the
new component reader required compact JSON plus LF. This was independently
reproduced before final sealing. Both attempts were deliberately interrupted
afterward to avoid more computation on a known unsealable source. Their
INCOMPLETE outputs and original bytes are retained. The resulting interrupted
phase codes are not natural numerical failures or completed Linux full-suite
results. Windows had completed its development suite (1482 passed, 14 skipped,
294 passed subtests); Linux had completed quality only. Neither profile passed.
A repaired source must use fresh environments and output paths, never rewrite
or reseal these attempts.

Final-source CPU and independent Linux clean-room evidence, actual rollback-v2,
complete policy-aware release aggregation/promotion, terminal CI confirmation,
and authorized real-GPU correctness/performance/fault evidence remain separate
gates. A fresh complete source-bound run, not the existence of these scripts,
establishes whether any particular gate passed. Historical C0 failures and old
attempts remain unchanged. No `v0.2.0` tag is permitted until every release gate
actually passes; the staged V0.0–V3.1 learning objective remains in force.
