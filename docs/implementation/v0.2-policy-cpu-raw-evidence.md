# CPU 原始数值证据：从测试通过到可以重新计算

本页是获批 CPU 范围内的开发工具说明，不修改冻结的
[数值协议](v0.2-numerical-policy-protocol.md)或历史失败。
包版本仍为 `0.2.0.dev0`、`DEVELOPMENT_ONLY`、`unqualified`。
GPU 暂缓，历史累计 GPU 预算仍待核清。不得据此创建 `v0.2.0` 发布标签。

## 为什么还要保存原始数据

JUnit 能说明某次断言是否通过，却不能让离线读者重新计算误差。
`validate_policy_cpu_raw.py` 把固定公开 tiny 输入、原有权威文件和实际执行得到的
原始张量字节一起保存。另一进程只用 Python 标准库重新计算误差、采样状态、
完整序列、缓存前缀与错误反例结果；不读取本地历史运行目录，也不生成新 golden。

| 工作进程 | 职责 | 独立性边界 |
|---|---|---|
| native | 未改动 A 与普通 Transformers D-native，各自完整生成 | 不加载候选 PolicyDecoder；另存普通 forward logits 与 trace adapter logits |
| candidate | B 全量重算、C 真 KV，各自按实际输出推进 | 保存每步全部适用算子、实际 C prefix、fence、资源和采样状态 |
| formula | 七组完整 FP64 公式与一组 RoPE 边界原语 | 独立加载校验权重；不导入 A/B/C、KV 实现或 Transformers |
| mutations | 九种故意错误及实际触发位置 | 错误输入、修改后原始观察和拒绝信息都保留，不只保存一个 `caught=true` |
| reproduction | 原有 tiny20 的 B/C 新进程复跑 | 重新执行；比对原始字节、完整 token 与状态，不复用前一进程结果 |

普通案例包括冻结 tiny50 和原有 tiny20。高精度 `high-05` 只做 position31/32
RoPE 原语，不伪造非零起点的公开生成请求。三个原有 op authority 保持原字节；
position255 边界也不伪造有已提交前缀的 KV 请求。

## 运行方式

先按 [CPU checkpoint runbook](v0.2-policy-cpu-checkpoint.md)创建未使用过的
source-bound CPU 环境。源码有任何变化都要重新 bootstrap，不能复用旧 manifest。
下面是独立于旧 `inputs → cpu → verify` 开发检查的原始证据入口：

```sh
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python scripts/validate_policy_cpu_raw.py --output out/policy-cpu-study-r1/raw-numerical
python scripts/validate_policy_cpu_raw.py --verify-existing out/policy-cpu-study-r1/raw-numerical
```

输出目录必须不存在，父目录必须已存在。收集要求 finalized source-bound manifest，
显式 CPU 和离线依赖；它没有 GPU 开关。各实际 worker 分进程执行，保留命令、
stdout/stderr 和返回码。失败不覆盖、不重签旧结果，保留 `INCOMPLETE` 与现有日志。
数值失败可以完整封装为失败证据，不能把容器的 `COMPLETE` 当作数值通过。

## 如何读输出

先看 `numerical-report.json` 的 `cpu_results`，再按 `comparisons.jsonl` 的
case/step/op/position 定位对应 worker pack。pack 以原生小端 FP32/FP64 字节保存，
有 dtype、shape、offset、length、SHA256 和语义 ID，不把摘要冒充原始张量。
BF16 提前转换的故意错误另在 mutation worker JSON 中保留原始 BF16 hex、shape、
长度和摘要；不能把它重标为 FP32 的 pack 数据。

比较记录保留 expected/actual shape、dtype、原始摘要、容差、首差位置、首差值、
最大绝对/相对误差、mismatch/nonfinite 计数和 bitwise 结果。expected 决定相对误差
方向；FP64 oracle 不先降为 FP32。attention 比较使用合法 prefix，完整保存的
未来位置还要单独检查 mask/概率。shape 不匹配不能通过 flatten、裁切或广播规避。

三种问题分开看：

1. 硬门：B/C、独立 native/FP64、原始 authority、KV prefix、错误注入等是否成立。
2. 逐元素兼容：新策略相对旧 A 是否满足原阈值，不因 token 相同而跳过。
3. 序列兼容：每条路径自由生成的完整序列和采样状态是否满足合同，不 teacher-force C。

CPU 子结果可以分别是 pass/fail。完整报告的这三个总轴保持 `incomplete`，因为
真实模型 BF16/FP16 GPU 门尚未执行；总体 `status` 为 `incomplete` 或实际 CPU 失败时
的 `fail`，不会在缺 GPU 证据时输出完整协议 `pass`。

## 离线复制与信任边界

`authorities/` 只含冻结的公开输入、合成 tiny 权重、原有 op tensors、协议和批准回执。
这些是数值证据，不改变 metadata-only R0 capture 的隐私或 replay 能力。
不应把此工具用于私有 prompt/真实模型 raw 数据而不重新审查数据保留策略。

收集时分别用源码 reader 和复制的最小 reader，在两个新 `-I -S` 进程中重算。
reader 拒绝 tensor 包导入和 socket 事件。复制完整目录后可以用其 `reader/`
里的 `illm.policy_cpu_raw_bundle.verify_bundle(Path(...))` 直接只读核验；调用前
把复制的 `reader/` 加到 `sys.path`，并设置 `sys.dont_write_bytecode=True`。
不需要原 checkout、原环境、Torch、Safetensors 或网络。

哈希、封口和重复重算证明内部一致性，不证明第三方来源真实性。只执行可信来源的
reader 源码；修改源码和所有哈希后重新签一个自洽目录不构成独立认证。
`--verify-existing` 先用当前可信实现核验外层 seal，再启动复制 reader。
符号链接、reparse point、证据文件 hardlink alias、额外文件及未列空目录都拒绝。

旧三阶段开发驱动仍如实报告 `raw_tensor_evidence=not_captured`：它没有运行本入口。
本入口也没有完成正式 profile/release3/rollback-v2 集成、最终跨平台 clean-room、
真实 GPU correctness/benchmark 或完整发布验收。它不是性能领先证明，也不是交互式 UI。
