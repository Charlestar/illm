# V0.2 数值执行策略：待确认的修订提案

> 状态：**方向 B 已认可；具体协议待批准，未实现、未改变当前验收标准**。
> 当前 V0.2 GPU 结果仍是 failed / unqualified；本提案不是发布豁免。
> 2026-10-21：用户明确回复“认可方案B并继续推进目标”。依本草案的分阶段
> 约定，现继续完善协议及规范拟稿；不将方向认可扩大为未知细节的实施授权。

## 审核摘要

数值契约说明“计算怎样执行、允许多少误差、什么结果才算通过”。本草案拟将
执行方式独立版本化，分别验证模型语义、同策略的 cache 等价性和旧实现兼容性；
不改变模型结构、权重、tokenizer 或采样算法。

唯一拟放松的发布门是：**是否允许新旧路径的低精度逐元素比较
仍然报告失败，但不再单独阻断发布**。直接 B↔C 数值比较、固定用例完整
greedy 序列、独立语义验证、资源安全和实验预算继续为硬门。

具体执行语义、输入身份、独立 oracle、命令接口及预算停止规则见
[协议附件](v0.2-numerical-policy-protocol.md)，规范落地文字见
[SPEC v3 amendment 拟稿](v0.2-spec-v3-amendment-draft.md)及
[ADR-007 拟稿](v0.2-adr-007-draft.md)。它们仍是待审批文档，不是当前能力。
本草案的方向认可只允许继续完善规范草案；附件冻结并再次明确批准后，
才允许更改正式 SPEC/ADR、编码或启动 GPU 实验，不能一次性授权未知硬门。

建议先审阅 §3 的兼容性取舍、§8 的 SPEC 逐节变更和 §11 的确认卡。
rowwise eager 只是待评估候选，不是已通过的方案，也不是已承诺的高性能后端。
本轮只更新提案、协议附件和规范拟稿；正式 SPEC、ADR-005/006、代码、阈值、
历史失败记录和标签不动。预算余额未核清也是独立的 GPU 启动阻断条件。

## 1. 为什么需要讨论契约

V0.2 要把全量重算改成真正的 KV 增量计算。数学上，同一位置的结果应当
相同；但低精度浮点实现还受具体归约顺序和 kernel 选择影响。当前的
[SPEC](../specs/versions/v0.2-stateful-streaming.md) §3.2 和 ADR-006 要求旧
V0.1 full-context 路径不变，又要求 cached 单 token 路径直接满足同一
逐元素 tolerance。我们不能为了发布，悄悄把失败改成通过。

[PyTorch 2.8 数值精度说明](https://docs.pytorch.org/docs/2.8/notes/numerical_accuracy.html#batched-computations-or-slice-computations)
说明数学等价的整体计算与切片计算不保证逐位相同。这支持调查执行方式，
不证明本项目偏差都合理，更不自动修改既定 tolerance。

目前实际诊断定位到：在同一份输入、权重和 dtype 下，旧 full-context
projection 的结果会随矩阵行数变化。当前 cached 实现只计算一行，不能
假装仍计算原先的所有行。这个观察支持讨论数值契约，**不构成“所有可能
实现都无法修复”的数学证明，也不排除还需要继续寻找实现问题**。

本地可核验的补充实验全部标记为 development / formal=false：

| 实验 | 有界观察 | 不能据此声称 |
|---|---|---|
| r18，真实一行的 12 种 PyTorch 原语 | 没有复现旧两行 Q projection | 未来所有 kernel 都不可能通过 |
| r19，cached-only separate bias | 仍越过 probability tolerance | 分离 bias 是正确修复 |
| r20，hello 第一层控制实验 | mask、K/V 相同；替换为旧 Q 后 scores/softmax/context/O 与旧路径一致 | 20 个 prompt 全部只有这个首因 |
| r21，共同 FP32 contraction 试验 | A/B、B/C、A/C 均未通过原 logits tolerance | 换成 FP32 或只比较新路径即可发布 |

```text
r18 4e7a74a7dc61e707a532716b1204b960bd4ec76e14861d3c441856ba313b6ad4
r19 5e9923a44ee1218ab6300bbcfe66f9a03f522fba209a2c09f05bd4242be47e4f
r20 8b21dd2571a5b5e3c5981ef8972a234dc0c0817c2e437e5ed94958cc8f38aae6
r21 a8b16a7e237c3db94e4154d50910bed5927b5b7aeec8646760f1d095fcbb1f62
```

文件名与完整上下文见 [数值调查](v0.2-numerical-investigation.md)。这些本地
诊断不是可移植发布证据；正式验收必须重跑并封存原始事实。

## 2. 两个方向

### A. 保持现有契约

继续寻找能直接满足旧 oracle 的实现。不能扩大 query、补齐上下文矩阵、
重算缓存 prefix，再把它统计成只处理一个 token；不能放宽阈值或换 oracle。
在找到通过实现前，V0.2 GPU 保持失败，不发 `v0.2.0`。

### B. 批准显式数值策略修订后再实验

保留 V0.1 的 Engine、`generate`、model/weight/tokenizer identities 和原
full-context forward 完全不变。为 V0.2 的新 facade 单独定义不可变的
`NumericalExecutionPolicy` ID/digest，而不是覆盖旧模型身份。

一个待评估的诊断候选是 **rowwise eager policy**：Q/K/V/O、MLP
gate/up/down、两次 layer norm、final norm 和 LM head 的行内执行规则均须
预先定义；QK/PV 和 softmax 只对合法 causal prefix 归约。必须明确 full
control 是否生成全部位置 logits，并据此计成本，不能只说“相同行内规范”
就推导两条路径一致。

新的 candidate full-recompute control B 每步仍重算所有位置，cached C 只算新增
query。B 在获批并通过独立验证前不是新的权威 oracle。不得把 B 的重算
混入 C，也不通过补零伪造 query_tokens=1。若采用新策略，`none` 必须与
显式 policy ID 一起选择 A 或 B，不能让一个未区分身份的 `none` 同时指
两种计算；原 A 的请求开始前回退路径仍需保留。

这个候选不要求先引入自写 CUDA，却可能显著增加 eager kernel 启动次数、
降低 prefill 性能。它是否消除全部差异、是否保留旧 greedy 序列都尚未证明。
若需要自写 kernel 或新增依赖，应再作独立范围评审，不自动扩展本提案。

## 3. 必须明确批准的兼容性取舍

区分三条路径，不能偷换名称：

```text
A = 冻结的 V0.1 Torch eager full-context 实现，按既定 device/dtype 执行
B = 新策略下尚未验证的 candidate full-recompute control
C = 相同新数值策略下的 contiguous KV 增量实现
```

当前已经实现但 GPU 验收失败的 cached 路径另记为 **C0**；C 专指尚未实现的
新策略候选。现有 A↔C0 的失败保持原样，不能改名成为新策略的通过记录。

如果选择 B 方向，需明确讨论是否允许把 **A↔B、A↔C 的低精度逐元素
tolerance** 从发布硬门改为单独的旧实现兼容性报告。没有这项明确批准，
现行 A↔C0 失败仍会阻止按旧合同发布；新增策略自身通过不能覆盖它。

| 比较 | 当前契约 | 方向 B 的待批准变化 |
|---|---|---|
| A↔cached 逐元素低精度 logits | A↔C0 是现行发布硬门 | 新的 A↔B/C 拟改为独立兼容性报告；C0 退出新策略发布候选，其历史失败不改标 |
| 固定 greedy 完整序列 | A↔C0 必须一致 | A/B/C 均为硬门，不把一个相同 token 当成完整序列通过 |
| B↔C 增量状态与 logits | B 尚不存在 | 新策略直接硬门；须独立语义验证，不能自证 |

本草案拟保留的硬门包括（批准前仍执行现有全部门槛）：

- 既有 V0.1 golden suite 的身份、digest 和预期结果不变；tiny 的冻结逐 op/
  greedy authority 与真实模型 fixed-20 分别验证，不把所有旧 golden 限定成 tiny。
  真实模型 20 个固定输入的完整最多
  8-token greedy 序列仍与 A 完全一致，不能只检查首个相同 token。
- B↔C 的 tiny CPU 50-case 每步 logits、token、position、RNG、terminal
  和资源比较；真实 GPU 维持 20 个固定输入、每个最多 8 个输出的 BF16/
  FP16 smoke。这里不是自动新增 GPU 50-case；若新增，须单列范围与预算
  审批。预注册 tolerance 数值不扩大，也不能从“各自接近 D”推导“B 与 C
  相等”，必须直接比较。
- 独立高精度/Transformers 语义校验、逐 op 首差、不同进程复现和故意错误
  注入。新的验证协议必须在正式运行前冻结，不在看到失败后修改。
- 实际 256/64 query 工作量、时间、显存及 telemetry off/on 原始数据；
  不保证提速，不把额外转换、临时张量或启动开销藏进 reference。
- policy ID、accumulator/storage/boundary dtype、运行环境和成本进入
  MemoryPlan、capture、数值报告、benchmark 与 release manifest。

旧兼容性报告若未通过原 tolerance，必须保留失败标签和最大误差等数据，
不能继续称为“与旧 A/V0.1 reference 数值等价”。如果 greedy 硬门也不通过，
候选直接 no-go，不在本提案内自动放松。

## 4. 成本与明确的 no-go

SPEC 的预算仍是 **1 GPU-hour**。方向 B 的正式矩阵拟明确采用 **B 与 C**，
不是在原矩阵之外再偷偷增加完整 A 基线。矩阵是 4 组 ×（3 次 warmup +
7 次 measured）× 2 个 suite × 2 个 dtype，即 160 个完整 256/64 请求。
其中 none 每请求重算 `sum(256..319)=18,400` 个 token-row，contiguous
每请求处理 `256+63=319` 个。全矩阵约 1,497,520 个 token-row；若字面
按单行启动 24 层的 7 个 linear，仅这部分就约 251,583,360 次调用，尚未
计 norm、attention、head、检查与 capture。因此 **不预设朴素 row loop
具有可接受性能，更不预设它适合成为默认后端**。

任何候选编码前先冻结执行语义和估算公式；编码后先做预注册的 tuning-only
探针，不查看 held-out。拟议探针为：BF16/FP16 × 四组，每组 1 warmup +
1 measured，共 16 个完整 256/64 请求、8 次初始化；先执行成本主导组，
必要时提前 no-go。它不改变正式矩阵的 3/7 次数，也不授予正式基线通过。
同步计时边界、执行顺序、保守外推和安全余量须在运行前登记；不得只用
一条最快结果估算，capture/export 与 dtype 转换均计入所在路径成本。

3600 秒上限拟覆盖此次实验的累计 GPU 占用墙钟：候选探针、A/B/C 校验、
独立 oracle、正式矩阵、初始化、失败尝试/重试及安全回收；不是每个候选
各送一小时。启动前核对已有消耗，不把未知历史用量自动算成零或重置预算。
探针 8 次与正式矩阵 16 次初始化分别计入；若另测完整 A 性能基线，须
重算请求数并另行确认范围。历史诊断耗时与新实验分列，不冒充正式矩阵。

每个新任务启动前检查剩余预算，预留 fence/资源回收与安全余量。
预计总成本超过可用余额、不能完成 64 输出、OOM 或正确性失败，立即 no-go；
到达预算阈值时不再启动新任务，已 launch 的工作仍须安全回收。
不得降低 repetitions、少测 dtype/组、缩短上下文或跳过 held-out 得到通过。
held-out 一旦用于调参，不能修改候选后仍称同一结果为未见验证；须重新
确认验证计划。增加预算或换策略需另行确认，不自动扩展本提案。

## 5. 分阶段确认与实施顺序

1. 先审阅本架构草案。方向认可后补齐具体 policy、suite 身份、独立 oracle
   与测试协议附件，同时准备 SPEC/ADR 拟稿；此阶段仍不改正式规范或实现。
2. 协议附件冻结并再次明确批准后，才修订 SPEC/ADR、提升 `spec_version`，
   逐条列出替代与保留门槛。V0.1 历史文件、标签与证据包不动。
3. 再做显式 development-only 候选，跑 A/B/C 对照及独立语义验证；未通过
   就保留失败，不把候选切成默认值。
4. 候选通过后补齐 policy 的类型边界、成本模型、事件/证据身份和负测试，
   重新冻结源码。旧 manifest 不复用。
5. 重跑 CPU、BF16、FP16、Linux clean-room、回退、可移植验证和最终 CI，
   完成发布审计之后才创建新标签。

这项决定影响的是 V0.2 的数值兼容性定义，不是允许删掉 GPU 验收，也不是
允许用 tiny/FP32 代替真实低精度模型。方向 B 已认可；具体协议获准落地前，
正式合同仍原样有效，不启动 B/C 实现或 GPU 实验。

## 6. 拟议的数值策略对象与选择规则

拟新增 `NumericalExecutionPolicyV1`，以 canonical JSON 计算 instance digest。
下列是待批准的字段约束，不是已注册 ID 或可执行配置：

| 契约内容 | 批准后、编码前必须冻结的值 |
|---|---|
| family/version | legacy 与候选策略分别命名；改变执行语义即新版本，不能覆盖同一个 ID |
| dtype/cast | 参数、KV、activation 的 storage dtype；逐 op accumulator、输出边界 dtype 与 cast 时刻；不得暗中把整个模型改为 FP32 |
| linear/norm | Q/K/V/O、MLP gate/up/down、LM head 的行形状；bias 是否融合；RMSNorm 的归约轴/次序/精度 |
| attention | 绝对 position、causal 合法区间、GQA 映射、QK/PV 归约；softmax 的 dtype/次序；RoPE FP32 `inv_freq` 契约 |
| layout/flags | stride/contiguous 规则；TF32、低精度归约、determinism flags；不依赖未记录的进程全局默认值 |
| schedule/logits | B 每步重算全部 prefix，生成全部位置 logits；C 只处理新增 query。调度差异不改变同位置的运算规则 |

BF16 与 FP16 属于同一 policy family，但 storage dtype 不同，因此 instance
digest 不同；同一 profile 的 B/C 必须共享 instance digest。硬件、driver、
Torch/CUDA 与实现 source digest 单列于运行环境身份，再与 policy 组合绑定；
不能把环境不同误当成同一环境的数值证明，也不承诺跨平台逐位复现。
policy 同时定义 none/contiguous 的调度规则，实际选择的 KV mode 单列记录，
不将这一选择混进 B/C 必须相同的 instance digest。

| numerical policy × KV mode | 路径 | 拟议用途 |
|---|---|---|
| legacy × `none` | A | 旧权威与明确回退，不修改 V0.1 |
| historical/unrecorded × `contiguous` | C0 | 只保留既有开发诊断；不注册为新legacy可发布组合，原失败不改写 |
| candidate × `none` | B | 尚未验证的完整重算 control，不先称为权威 oracle |
| 同 candidate × `contiguous` | C | 真正增量候选；通过全部门槛前不成为发布默认 |
| missing/unknown 新策略 | 无 | 新格式/新请求在执行前 fail closed，不静默选择默认 |

`none` 是 KV 模式，不是完整数值身份。拟议配置必须同时明确 policy；
当前 CLI 尚无此选择接口，本表不能当成已支持的命令。请求 acceptance
之前冻结选择，运行中不热切换。旧 model/spec/weight/tokenizer ID 以及
`none-reference-full-context-v1` 的历史含义均不改变。

## 7. 拟议验证协议：比较什么、谁决定通过

### 7.1 对齐点与原阈值

prefill/output0 对齐同一绝对位置；decode 将 B 最后一个绝对位置的行与 C
当前 query 行直接比较。覆盖逐层 Q/K/V、RoPE、scores、probabilities、
context、O、MLP、final norm/logits；C 的 cached prefix K/V 另与 B 对应
绝对位置的 K/V 比较。不能用 B≈D 且 C≈D 推导 B↔C 直接通过。

`expected` 方向预注册：B↔C 以 B 为 expected，旧兼容性以 A 为 expected，
独立 oracle 比较以 D 为 expected。沿用现有逐元素公式：
`abs(actual-expected) <= atol + rtol*abs(expected)`，不改为事后更宽的公式。

| profile/tensor | atol | rtol |
|---|---:|---:|
| tiny FP32，逐 op/logits | 1e-4 | 1e-3 |
| real BF16，activation/logits | 0.0625 | 0.02 |
| real FP16，activation/logits | 0.0078125 | 0.01 |
| real BF16，attention probabilities | 0.005 | 0.02 |
| real FP16，attention probabilities | 0.001 | 0.01 |

继续检查 shape/dtype、非有限值与合法 causal `-Inf` sentinel；不能因为忽略
masked 区域而容许错位 mask。逐 op 全采集的用例/位置、独立 oracle 范围与
相应预算在探针前登记；不隐式扩展成新的 GPU 50-case 全量测试。

### 7.2 直接验证与独立 oracle

下表给出架构级硬门与角色，不冒充已经冻结的可执行协议。所有待补的 suite
身份、D-high 构造、采集位置与阈值均须先完成协议附件、再次审批，才能执行。

| 验证项 | 固定范围 | 拟议发布效力与证据 |
|---|---|---|
| 既有 V0.1 golden | 原 suite ID/digest/预期值；tiny authority 仍为 `d424fe676820b748bf51023ca15150211d3414371314d63ce3fa647c4264fadc`，real fixed-20 另行绑定 | 硬门；保留原结果，不重新生成 golden 来适配候选 |
| 既有 A↔C0 失败 | 原报告、原阈值、原源码 | 修订批准前仍 blocking；批准后 C0 不进入新策略发布候选，但其历史 fail/INCOMPLETE 永不改标 |
| B↔C 直接 differential | tiny CPU 50 个不同边界 case；real GPU 固定 20 输入、各最多 8 输出，BF16/FP16 均测 | 原 tolerance + token/state/RNG/terminal/resource 硬门；输出逐步原始比较 |
| A/B/C 固定 greedy 兼容 | 两种 real dtype 的完整 fixed-20 序列，含 EOS/length 终止 | token IDs、输出数和 finish reason 精确一致；单个相同 token 不算通过 |
| A↔B、A↔C 低精度逐元素 | 同步固定输入与语义位置，使用原 tolerance | **仅此项拟改为 report-only**；仍标 `comparison_result=fail`，保存首差 op、超差数量、max abs/rel，不称 numerical equivalent |
| D-native 独立验证 | 普通 Transformers full-context/batched 路径，非候选 rowwise 改写；按 ADR-005 原生 dtype 构造 | 硬门；原阈值，独立加载验证后的 safetensors，保留 FP32 RoPE buffer；用例/位置须写入协议附件 |
| D-high-precision 语义检查 | 预注册的公式、position/mask/GQA/RMSNorm/MLP/tied-head 边界用例 | 硬门；构造、tensor 对齐及阈值事先冻结；不替代 BF16/FP16 直接比较 |
| 错误注入/独立进程 | wrong transpose、KV position、policy mismatch 等固定反例；同 profile 的独立进程复现 | 硬门；必须在相应 op/身份校验捕获，不能只检查最终文本 |
| 生命周期与性能证据 | 既定 100-cycle/fault matrix、256/64 四组 × 两 suite × 两 dtype | 全部保留；预算/资源安全硬门，提速不是发布条件 |

D-native 按 ADR-005 使用 pinned Transformers native-dtype factory，不复用
B/C 的模型模块、KV、已计算 tensor 或可能带同一错误的 helper。
D-native **仍使用普通 full-context/batched 执行**，不悄悄改成候选 schedule。
因此它可能因同类形状相关舍入继续否决 B/C；本草案保守地保留此硬门，
**不保证采纳方向 B 就能解锁 GPU 发布**。若要把 D-native 也降级、替换
或改为 rowwise oracle，属于另一项验收取舍，必须另外说明并批准。
D-high-precision 单独标明不同计算精度；它检查数学语义，不把 FP32 结果
冒充真实 BF16/FP16 执行。任何 D 硬门失败仍 no-go，不能运行后另选更宽阈值。

兼容性报告与发布资格采用独立结果轴。兼容性逐元素失败不能令测试在首个
decode 就停止，而后声称完整 greedy 序列一致；应独立完成序列检查。
若因 OOM、非有限值或执行异常无法完成，记失败/未完成，不推断剩余输出。
原 A↔C0 的 `INCOMPLETE` 报告继续保存；新协议必须重跑 A/B/C，不将旧失败改标通过。

## 9. ADR 拟案：新增 ADR-007，不覆盖历史决策

拟题为 **Versioned numerical execution policies for V0.2**；本节只是拟案，
尚未创建正式 `docs/adr/ADR-007`，编号在落地前再次确认。

- **Status**：proposed；具体协议附件冻结并再次明确批准后才 accepted，不由“允许写方案”或方向认可推导实施授权。
- **Context**：冻结的旧 full-context 与增量执行出现形状相关低精度差异；目前证据不能证明所有实现都不可能满足旧合同。
- **Decision**：将执行策略独立版本化，采用 A/B/C/D 验证分层；唯一拟降为非阻断的是 A↔B/C 的旧逐元素兼容结果，原阈值与其他硬门保留。
- **Supersedes**：仅在 V0.2 新策略作用域替代 ADR-006 的隐含 oracle/fallback 与数值验收路由；ADR-006 的状态、资源、流式和 R0 规则继续有效。ADR-005 对 V0.1、阈值、sampler、独立 oracle 的权威不变。
- **Alternatives**：继续方向 A；或评估已冻结语义的 eager 候选。rowwise 不预设为最终选择；新增 CUDA/Rust/Triton、依赖或预算需独立批准。
- **Rejected shortcuts**：放宽阈值、以一个 token/FP32/tiny 替代真实 GPU、只比较共享错误的 B/C、伪造 query=1、少测矩阵、改写失败历史。
- **Consequences**：新增身份/格式/验证复杂度，可能更慢或 OOM；不承诺聊天质量、跨平台逐位相同或性能领先。
- **Qualification/no-go**：完整执行 §4/§7；任一硬门失败不得默认启用或发布，失败候选/日志保留。
- **Rollback**：只在新请求前选择 A+none，等待已知完成与安全回收；未知 fence 保留 quarantine，回退不能使未知资源变成零。

## 10. Capture、报告与回退的拟议兼容边界

policy 身份进入 MemoryPlan、live result、capture、数值报告、benchmark 和
release manifest，但不能静默给旧 schema2 增加新的必填语义。
本草案建议 policy-aware capture 使用**新的格式版本（拟为 schema3）**及独立
catalog/revision；envelope v1 与最高 `[R0]` 能力保持。格式版本不是 replay
能力等级，schema3 不代表 R3。报告/release 元数据也须明确修订号；具体
字段与版本在批准后的规范变更中先冻结，再编码，并更新真实版本分派测试。

旧 schema0/1/2 继续各自读取；schema2 缺少 policy 时按历史格式及已记录的
KV mode 展示，数值策略标为 legacy/unrecorded，不能套用新默认、补写 manifest
或声称其原本记录了新 policy。推导的 legacy 标签只是派生说明，不是原始数值
证据，也不能使旧证据满足新门槛。新格式缺失/未知 policy 的执行与数值验收
fail closed。旧 V0.1 binary 对新格式明确拒绝，不能伪造支持。
旧 schema2 的 `policy_id/digest` 保持未记录（派生视图可显示 null/unrecorded），
不能追认成一个真实旧 policy ID。§6 的 legacy 组合指未来按显式策略复跑的
旧执行语义，不表示历史证据已经记录过该身份。

改 policy 不能复用 KV、MemoryPlan、编译/派生缓存或旧环境 manifest；模型
权重仅在 digest 完全一致时复用。隔离回退仍需独立旧 binary/environment、
最后安全 request ID、原始日志、11 项真实资源计数和 config/manifest digest。
R0 展示成功与数值资格分别验证，不以能读时间线推导能复算或数值兼容。
