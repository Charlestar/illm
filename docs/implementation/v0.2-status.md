not a release manifest and does not grant CPU, GPU, clean-room, or tag status.

### Explicit policy CPU development slice

New pure-stdlib policy/input registries bind the approved descriptors and exact
input-only snapshots. Separate `PolicyDecoder` B/C arithmetic uses per-row FP32
contractions, profile-storage boundaries and real committed KV. An independently
loaded CPU FP64 formula oracle checks tiny mathematical semantics; it does not
replace native Transformers or real BF16/FP16 GPU validation.

The streaming Python facade accepts an explicit `numerical_policy` object.
Without it, the previous C0 development surface remains unchanged; no candidate
was silently made default. Explicit results/metadata use schema3, policy-aware
MemoryPlan uses schema2, and the old result schema2 keeps its original fields.
The new [CPU example](../examples/v0_2_policy_cpu.py) compares B/C query work.
The [CPU checkpoint runbook](v0.2-policy-cpu-checkpoint.md) describes the
source-bound `inputs` → `cpu` → `verify` development driver and its limits.

The CPU policy-aware schema3 capture writer and tensor-free offline reader are
implemented separately from schema2, with strict policy/protocol/execution/
MemoryPlan identity binding. Versioned R0 Request Story, Chrome trace and derived
PNG/SVG views retain those identities. The CLI opts in with `--numerical-policy`;
omitting it preserves C0. See the [capture example](../examples/v0_2_policy_capture.py).
Earlier CPU checkpoint evidence belongs to its recorded source, not this change.

Full raw numerical-policy/benchmark reports, formal portable qualification,
qualification/release3 and rollback-v2 migration, and final-source release
profiles remain pending. Explicit-policy CUDA requests still fail before model
loading. Development checks and CPU reports do not grant final CPU, GPU or tag
qualification; schema3 remains exactly R0.

The real-model first-divergence facts, rejected diagnostic hypotheses and
reproduction tool are documented in the
[CUDA numerical investigation](v0.2-numerical-investigation.md). Both original
failures remain failures; neither scope nor tolerance was weakened.

## Reproduce the development surface safely

The runtime artifact alias remains `v01-cpu`; that name identifies a dependency
lock, not V0.1 qualification. Environments are bound to the exact project source
digest. Never copy an environment from an old checkout or reuse an old manifest
after source changes.

Use CPython 3.12.14 for the locked Windows profile or 3.12.3 for locked Linux.
Bootstrap one fresh profile for the current source, then run every child command
through its manifest:

```sh
python scripts/fetch_runtime.py --runtime-profile v01-cpu --artifact-cache .illm/cache/runtime
python scripts/bootstrap.py --profile study-v02-current --runtime-profile v01-cpu --artifact-cache .illm/cache/runtime --locked --offline --write-manifest out/study-v02/toolchain.json --write-manifest-digest out/study-v02/toolchain.sha256
python scripts/in_env.py --manifest out/study-v02/toolchain.json --expected-manifest-digest-file out/study-v02/toolchain.sha256 -- python -m illm verify --fixture tiny-decoder
python scripts/in_env.py --manifest out/study-v02/toolchain.json --expected-manifest-digest-file out/study-v02/toolchain.sha256 -- python -m illm run --model fixture:tiny-decoder --prompt hello --max-new-tokens 4 --seed 7 --stream
```

If the source, lock, interpreter, environment root, manifest digest or handshake
differs, the runner must fail before project code executes. A convenient local
`PYTHONPATH=src` run is useful for development only and is never release evidence.
