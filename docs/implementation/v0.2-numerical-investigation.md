# V0.2 CUDA numerical investigation

> 2026-10-21 development observations. **Unqualified; unresolved.**
> These runs are not a source-frozen release profile. Their failure is preserved;
> no tolerance, scope, model revision, or published V0.1 artifact was changed to
> convert it into a pass.

## What actually failed

The RTX3070 / PyTorch2.8.0+cu126 development environment executed both fixed real
model profiles. The predeclared scope was `real-smoke`: 20 fixed public prompts,
greedy generation, up to eight outputs per prompt. The differential producer
stops each case at its first discrepancy; therefore these reports **do not prove
eight-token agreement** after the discrepancy.

| Run | First failing case / output position | Observed last-row logits | Result |
|---|---|---|---|
| BF16 | `fixed-greedy-00`, position1 | max absolute error0.265625, 13,846 out-of-tolerance vocabulary entries; selected token330 in both paths | `INCOMPLETE` / fail |
| FP16 | `fixed-greedy-00`, position1 | max absolute error0.06640625, 11,780 out-of-tolerance vocabulary entries; selected token99466 in both paths | `INCOMPLETE` / fail |

The raw reports remain under `out/v02-stateful-gpu-bf16-dev-r1/` and
`out/v02-stateful-gpu-fp16-dev-r1/`. These ignored local development paths are
diagnostic locations, not portable release evidence.

Report digests:

Fences in the exercised steps completed, the query/KV lengths matched the
declared append contract, and executors closed back to zero resources. Those
facts are useful but **do not override the failed numerical check**.

## Locate the first difference, not just the final logits

`scripts/diagnose_stateful.py` independently records a full-context forward and
one cached decode, aligns their final query rows, and compares each canonical
operation. It also compares previously cached K/V with the corresponding
full-context prefix. Every result is explicitly development-only.

For `hello` in BF16:

- embedding and first input normalization are identical;
- the first exact difference appears in layer0 q projection (maximum0.0625);
- the first operation exceeding its frozen per-op tolerance is layer0 attention
  probabilities (maximum0.1015625);
- the cached-prefix K/V comparisons in this default-policy diagnosis remain
  within their frozen tolerances. This alone is not proof that all KV behavior
  is correct.

For the five-token public prompt `The capital of France is`, layer0 projection,
RoPE, scores, probabilities and attention context match exactly. The first exact
difference is the layer0 output projection, below its per-op tolerance. The first
threshold crossing appears in layer1 attention probabilities. A diagnostic must
not assume that every prompt has the same first divergent operation.

## Hypotheses checked, not fixes applied

Identical last-query input was evaluated with several padded GEMM row counts.
The two-row q projection matches the two-row full-context result, while one,
four, eight, sixteen and thirty-two rows differ in some BF16 elements. A
six-row full-context example shows a different grouping of exact agreements.
This is evidence of shape-dependent numerical behavior, **not yet a complete
root-cause proof** for the end-to-end discrepancy.

Two separate process-level experiments also failed to remove the discrepancy:
disabling FP16/BF16 reduced-precision reductions, and setting
`DISABLE_ADDMM_CUDA_LT=1`. Neither experiment changed the engine's default policy
or granted a profile. Blanket zero-padding to the whole old context would also
need its real compute cost disclosed; it must not be used to pretend that old
context computation was eliminated.

Follow-up controls also remain diagnostic failures, not fixes:

- explicit deterministic algorithms with `CUBLAS_WORKSPACE_CONFIG=:16:8` retain
  the same BF16 layer0 probability discrepancy;
- FP32 linear/QK/PV accumulation **only in cached prefill and decode**, cast back
  at each contraction, still fails directly against the unchanged V0.1 BF16
  reference (`v02-stateful-bf16-cached-contractions-r8.json`);
- the independent FP16 trace first crosses its probability tolerance in layer0,
  with maximum0.01513671875 (`v02-stateful-fp16-first-op-r10.json`).

A separate `--fp32-shadow` experiment converts the same fixed source weights to
an explicitly different FP32 model spec. Its one-prompt, one-decode diagnostic
has no per-op or prefix threshold crossing, but it is labelled
`fp32-shadow-not-a-low-precision-pass`. It is not eight-token coverage, not a
BF16/FP16 result, and not a replacement oracle. Both original low-precision
qualification failures remain in force.

PyTorch2.8 explicitly does not promise bitwise equivalence between batched and
sliced computations. That explains why a mechanism-level investigation is
necessary; it is not permission to ignore an iLLM acceptance failure. See the
[pinned numerical-accuracy documentation](https://docs.pytorch.org/docs/2.8/notes/numerical_accuracy.html)
and the [pinned addmm CUDA implementation](https://github.com/pytorch/pytorch/blob/v2.8.0/aten/src/ATen/native/cuda/Blas.cpp).

## Reproduce the diagnostic

Use a development environment with the locked CUDA dependency versions and local
fixed model assets. The following is deliberately **not** a formal qualification
command. Output paths must be new; the tool refuses to overwrite an old report.

```sh
PYTHONPATH=src python scripts/diagnose_stateful.py --model configs/models/v0_2.yaml --device cuda:0 --prompt hello --output out/my-v02-first-op.json
```

The tool restores the caller's thread and precision settings even on an error.
Its padding/reduction probes only diagnose execution; they do not change model
weights, the canonical sampler, the production cached implementation, or acceptance tolerance.
Experimental `--cached-policy fp32-contractions` instrumentation is scoped only
to cached calls and restores the original methods even on an exception. The
full-context reference call stays outside that scope; this is not a production
backend. Numerical-control environment variables are recorded from a small
explicit allowlist, not by dumping the process environment.

## Release decision

Both real-model profiles remain failed development observations. V0.2 still
requires a defensible implementation fix, fresh source-bound runs, the complete
release qualification chain and independent CI before the `v0.2.0` tag. A tiny
CPU pass, matching selected tokens at one failing step, or a green unit suite is
not a substitute for these missing facts.
