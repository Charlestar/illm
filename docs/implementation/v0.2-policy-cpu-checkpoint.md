# V0.2 explicit-policy CPU development checkpoint

This is an implementation and learning checkpoint under the
[human CPU-only approval](v0.2-policy-approval.md), not a V0.2 release or a
replacement for the frozen [numerical protocol](v0.2-numerical-policy-protocol.md).
The package remains `0.2.0.dev0`, **unqualified**. GPU work is deferred.

## What to study

| Question | Implementation / runnable check |
|---|---|
| Why does KV mode not identify arithmetic? | `src/illm/numerical_policy.py`: immutable dtype-specific descriptors and separate KV selection |
| How do full recomputation B and true-KV C differ? | `src/illm/model/policy.py`; [CPU example](../examples/v0_2_policy_cpu.py) prints query lengths `[6,7,8,9]` versus `[6,1,1,1]` |
| Why is agreement between B and C insufficient? | `tests/model/test_policy_numerical_protocol.py` compares both directly with native Transformers and retained golden tensors |
| What is the mathematical cross-check? | `src/illm/model/high_precision.py` independently loads verified tiny weights and executes FP64 formulas, without importing candidate arithmetic |
| What does the new arithmetic cost? | `src/illm/memory/policy.py` includes FP32 weight sidecars and prefix scratch; estimates are not measured allocator peaks |
| How is a result tied to what ran? | `src/illm/policy_binding.py`, result/metadata schema3, MemoryPlan2 and policy-specific event catalog |

The candidate is opt-in. Omitting `numerical_policy` keeps the previous C0
development behavior; explicit legacy+none preserves the old reference. The
frozen V0.1 model, sampler, goldens, tags, bundle and historical C0 failures are
not rewritten. A matching selected token alone is not numerical validation.

## Reproduce on a fresh CPU environment

Use the platform's locked Python patch release: Windows CPython3.12.14 or Linux
CPython3.12.3. The cache must already contain the `v01-cpu` artifacts. No network
or GPU is needed for these commands. Choose an unused profile and `out` root;
never delete a failed attempt merely to reuse its name.

```sh
python scripts/bootstrap.py --profile policy-cpu-study-r1 --runtime-profile v01-cpu --artifact-cache .illm/cache/runtime --locked --offline --require-new-environment --write-manifest out/policy-cpu-study-r1/toolchain.json --write-manifest-digest out/policy-cpu-study-r1/toolchain.sha256
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python scripts/run_numerical_policy.py --stage inputs --protocol docs/implementation/v0.2-numerical-policy-protocol.md --approval docs/implementation/v0.2-policy-approval.json --attempt out/policy-cpu-study-r1/attempt.json --output out/policy-cpu-study-r1/inputs
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python scripts/run_numerical_policy.py --stage cpu --protocol docs/implementation/v0.2-numerical-policy-protocol.md --approval docs/implementation/v0.2-policy-approval.json --attempt out/policy-cpu-study-r1/attempt.json --output out/policy-cpu-study-r1/cpu
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python scripts/run_numerical_policy.py --stage verify --protocol docs/implementation/v0.2-numerical-policy-protocol.md --approval docs/implementation/v0.2-policy-approval.json --attempt out/policy-cpu-study-r1/attempt.json --output out/policy-cpu-study-r1/verified
```

`--require-new-environment` makes bootstrap reject an existing environment.
The driver validates the finalized CPU manifest and current source binding; the
manifest itself is not a proof of fresh creation. This recipe supplies that
separate freshness condition. Any source change invalidates the run's manifest:
preserve the old attempt and bootstrap a new profile for the changed source.

`inputs` copies the exact approved input bytes and three registered candidate
descriptors. `cpu` runs whole-tree quality, all `pytest tests`, and the actual
public policy example with the finalized interpreter. `verify` rechecks the
ordered journal, source/toolchain identity, checksums and execution artifacts.
Reports retain commands, return codes, stdout/stderr and JUnit accounting.
Inspect `cpu/cpu-report.json`, `cpu/junit.xml`, `cpu/quality.json`,
`cpu/logs/`, and `verified/verification-report.json`; do not infer a pass merely
because an output directory exists.

Pytest scratch is a separate, newly owned sibling of the CPU output directory,
not sealed evidence. The exact relative scratch path is bound in the report and
command transcript. The driver refuses an existing or linked scratch root and
does not recursively delete it after testing. Preserve it for diagnosis; a
later explicit cleanup is separate from verifying the actual evidence files.

Outputs are exclusive and failures retain `INCOMPLETE`. A crash-left attempt
lock blocks progress; the driver does not reclaim a foreign/stale lock. Inspect
and resolve the interrupted attempt before choosing any manual recovery.

## Policy-aware R0 capture development example

The explicit CPU path now writes its own schema3 capture, not schema2 with
unrecorded arithmetic. The separate tensor-free reader validates policy,
protocol, execution binding and MemoryPlan identities. Derived Request Story,
SVG/PNG and Chrome trace retain these bindings and declare exactly R0.

Using the same freshly bootstrapped source-bound wrapper, run:

```sh
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python docs/examples/v0_2_policy_capture.py --output out/policy-cpu-study-r1/capture-demo
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python -m illm inspect request out/policy-cpu-study-r1/capture-demo/cached/capture --request cached --chrome-trace out/policy-cpu-study-r1/cached-trace.json
python scripts/in_env.py --manifest out/policy-cpu-study-r1/toolchain.json --expected-manifest-digest-file out/policy-cpu-study-r1/toolchain.sha256 -- python scripts/check_policy_capture_portable.py out/policy-cpu-study-r1/capture-demo/cached/capture --output out/policy-cpu-study-r1/portable
```

Every output root must be new. The example compares B/C query work and observes
safe cancellation; it is not a benchmark or live GPU profiler. The portable
check copies the verified capture and minimal reader, then reads it in fresh
`-I -S` processes without tensor libraries. It demonstrates portability, not
authenticity or formal numerical qualification. The CPU driver still records
quality, the complete pytest suite and the basic arithmetic example; this
additional capture example/check is separate development evidence, not an
already completed final release profile.

## Separate retained CPU raw evidence

A separate [raw numerical evidence tool](v0.2-policy-cpu-raw-evidence.md) now
collects fixed tiny CPU tensors and recomputes metrics in isolated stdlib-only
readers. It is not invoked by the three-stage development driver above; that
driver's `raw_tensor_evidence=not_captured` remains literal. The standalone tool
is CPU-only and unqualified, not the complete numerical/GPU/release profile.

At source `ec10eec`, a new Windows CPU environment completed the three-stage
development check (1352 pytest cases passed, 12 skipped; quality/mypy passed).
Its separate raw collection nevertheless remained `INCOMPLETE`: all five
workers completed, but the reader incorrectly required the toolchain UUID
`environment_id` to be a SHA256 digest. A copied-reader diagnosis is not a gate
pass and does not reseal that attempt. The narrow UUID-type correction requires
a new source-bound environment and complete collection/recomputation, not reuse
of those failed artifacts. This is a checker integration failure, not a reason
to change numerical tolerances, authority files or qualification boundaries.

## What a passing development check does not prove

The report kind is `illm-policy-cpu-development-gate-v1`, with
`evidence_mode=DEVELOPMENT_ONLY` and `qualification_tier=unqualified`. It is not
the full raw-tensor numerical-policy qualification report. CPU tests cover
frozen tiny suites, independent native/FP64/golden comparisons, real KV state,
RNG/state/resources, mutation sensitivity and fresh-process reproduction;
their JUnit success is not a portable replacement for the protocol's eventual
retained raw tensor artifacts.

Still pending are full raw numerical and benchmark reports,
qualification/release3 and rollback-v2, final source-matched CPU/clean-room
profiles, and all real-model GPU gates. CPU policy capture3 is implemented;
explicit-policy CUDA is rejected before model loading. The CLI remains C0 when
the policy selector is omitted. No policy is silently made default.

The GPU stages in the reserved CLI fail before project/Torch/model imports.
They cannot be enabled by changing an attempt journal or supplying a different
approval file. The human GPU deferral remains in force even if the historical
cumulative budget is later reconciled. Neither a CPU pass nor schema3 grants
GPU qualification, R3 replay, a speed claim, or permission for a `v0.2.0` tag.
