> V3.1 不再增加推理算法，而是把 V3.0 的完整能力变成可长期运行、可兼容升级、可排空替换、可回滚和可审计的稳定版本。可靠性只对本 SPEC 的 support matrix 与部署前提负责；它不声称成为计费系统、Kubernetes 平台或商业级多租户控制面。

## 1. 本版本学习目标

### 1.1 必须掌握

- 能够把“可靠”拆成明确的请求终结、资源守恒、可用性、恢复时间、兼容窗口、容量余量和证据保留要求。
- 能够实现 worker/service 的 generation-fenced 生命周期、readiness、drain、quiesce、replacement 和 fail-stop。
- 能够设计相邻版本协议协商、滚动升级、canary、回滚与不兼容 artifact 拒绝规则。
- 能够判断请求在未输出、已输出、KV transfer 中、collective 中等状态下是否可安全 retry，避免重复 token 和双 terminal。
- 能够建立 capacity plan，测量 KV/weight/workspace/graph/transfer/telemetry/queue headroom，并在过载前执行 hard admission。
- 能够设计 chaos、soak、overload、升级/回滚演练，使用 error budget 和恢复阈值判断版本是否可发布。
- 能够建立最小安全边界：默认私有监听、管理面隔离、认证、资源限制、模型供应链校验、capture 隐私和依赖/SBOM 证据。
- 能够编写 runbook 与 support/LTS matrix，清楚区分“已测试并支持”“实验性”“明确不支持”。

### 1.2 建议先修

- 已完成 V3.0 的 TP/DP/P-D、transfer ticket、generation、backpressure、unified fallback 与 distributed capture。
- 熟悉进程信号、健康检查、超时/重试、SemVer、向前/向后兼容、基本威胁建模和故障注入。
- 能运行固定硬件的 open-loop workload、读取置信区间，并区分预期拒绝、客户端错误和服务端失败。

### 1.3 进入门槛与预热实验

先执行 `python scripts/bootstrap.py --profile learning-cpu --locked --write-manifest out/v3.1-learning/toolchain.json`；下表的 CPU model-checking 实验均通过该 manifest runner 执行。

| 预热实验 | 命令/材料 | 通过标准 | 预计时间 |
|---|---|---|---:|
| Generation fencing model | `python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab generation-fencing --backend simulator --interleave all` | stale mutation 永不重新加入 routing | 2 h |
| Drain linearization lab | `python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab drain-race --backend simulator --in-flight-admission 32` | drain ack 后 accepted 增量严格为 0 | 2 h |
| Journal recovery lab | `python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab journal-recovery --backend simulator --fault each-durable-boundary` | operation 只执行一次或 safe-pause，无重复 replacement | 3 h |

术语见[统一学习术语表](../GLOSSARY.md)。这些 CPU model-checking 预热先通过，再预约昂贵的冗余 GPU chaos runner。

### 1.4 Teach-back 产物

- 一份《从 v3.0 滚动到 v3.1 再回滚》的时序图，标出 compatibility、drain、generation、readiness 与请求去向。
- 一份 24 小时 soak + chaos 复盘，解释每类错误是否消耗 error budget、资源是否回基线、为何可/不可自动恢复。
- 一份面向新维护者的“30 分钟接管演练”：依照 runbook 诊断 worker unhealthy、执行 replacement 并导出证据包。

## 2. 用户可观察的成果

### 2.1 Learning Demo (CPU/simulator)

该路径用 generation/drain/journal simulator 学习 stale fencing、linearization 与 crash recovery，不需要 GPU。第一条命令只 bootstrap；其余命令必须由同一个 manifest runner 执行：

```text
python scripts/bootstrap.py --profile learning-cpu --locked --write-manifest out/v3.1-learning/toolchain.json
python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab generation-fencing --backend simulator --interleave all --capture out/v3.1-learning/generation
python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab drain-race --backend simulator --in-flight-admission 32 --capture out/v3.1-learning/drain
python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm lab journal-recovery --backend simulator --fault each-durable-boundary --capture out/v3.1-learning/journal --write-manifest out/v3.1-learning/manifest.json
python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm ops runbook dry-run --fixture runbooks/v3.1/cpu-safe-pause.yaml --backend simulator --evidence out/v3.1-learning/runbook-dry-run
python scripts/in_env.py --manifest out/v3.1-learning/toolchain.json -- python -m illm release qualify --manifest out/v3.1-learning/manifest.json --profile reliable-ops-cpu-model-check-v1 --claim learning_complete --output out/v3.1-learning/learning_complete.json
```

`learning_complete.json` 必须标记 `hardware_class=cpu_simulator`，并引用 generation、drain、journal recovery、R1 digest 和 runbook dry-run evidence。它最多授予 `learning_complete`；不能满足 supported deployment、24/72 小时 soak/chaos、§12.2 的任何 Must、stable release 或 LTS promotion。缺少冗余 GPU runner 时，正式 profile 必须记录 `not_run_resource_unavailable`，不能显示 pass。

### 2.2 Hardware Qualification Demo

先建立两个互相隔离、都绑定 exact wheel digest 的硬件验证环境：source 只能运行 v3.0.0，target 只能运行 v3.1.0。固定的 V3.1 benchmark client 用 target 环境访问两者，排除客户端版本漂移；server lifecycle 命令必须使用与被控 server 相同的环境。除 bootstrap 外全部经相应 manifest runner：

```text
python scripts/bootstrap.py --profile release-verify --locked --artifact release/v3.0.0/dist/illm-3.0.0-py3-none-any.whl --artifact-manifest release/v3.0.0/dist/artifact-manifest.json --write-manifest out/v3.1-hw/source-toolchain.json
python scripts/bootstrap.py --profile release-verify --locked --artifact release/v3.1.0/dist/illm-3.1.0-py3-none-any.whl --artifact-manifest release/v3.1.0/dist/artifact-manifest.json --write-manifest out/v3.1-hw/target-toolchain.json
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm ops preflight --config configs/releases/v3.1/reliable-pd.yaml --source-toolchain out/v3.1-hw/source-toolchain.json --candidate-toolchain out/v3.1-hw/target-toolchain.json
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm support show --format table
```

先在相同冻结硬件预算上采集 V3.0 reference。在 **Terminal A** 前台启动 reference；`illm serve` 不 daemonize，默认只监听 loopback：

```text
python scripts/in_env.py --manifest out/v3.1-hw/source-toolchain.json -- python -m illm serve --config configs/releases/v3.0/unified-baseline.yaml --host 127.0.0.1 --port 8311 --control-file out/v3.1-hw/reference.control.json --capture out/v3.1-hw/reference
```

保持 Terminal A 运行，在 **Terminal B** wait-ready、运行 reference workload 并显式 shutdown；确认 Terminal A 以 0 退出：

```text
python scripts/in_env.py --manifest out/v3.1-hw/source-toolchain.json -- python -m illm server wait-ready --control-file out/v3.1-hw/reference.control.json --timeout-s 600
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm bench --endpoint http://127.0.0.1:8311 --workload fixtures/v3.1/reliability-smoke.jsonl --output out/v3.1-hw/reference-bench
python scripts/in_env.py --manifest out/v3.1-hw/source-toolchain.json -- python -m illm server shutdown --control-file out/v3.1-hw/reference.control.json --deadline-s 180
```

reference 完全退出后，先在同一冻结硬件上运行一个**独立 managed upgrade fixture**。它不连接后续 foreground candidate 的 control file：runner 在每轮前从 exact v3.0 manifest 冷重置 source generation，执行 v3.0→v3.1 rollout、验证，再执行 v3.1→v3.0 rollback、验证，最后销毁 fixture 并证明容量/进程归零：

```text
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm ops drill rolling-change --source-toolchain out/v3.1-hw/source-toolchain.json --candidate-toolchain out/v3.1-hw/target-toolchain.json --source-manifest release/v3.0.0/manifest.json --candidate-manifest release/v3.1.0/manifest.json --rollout-plan configs/releases/v3.1/rollout-from-v3.0.yaml --rollback-plan configs/releases/v3.1/rollback-to-v3.0.yaml --reset-source-before-each --evidence out/v3.1-hw/change-drill
```

drill 完全销毁且硬件回到基线后，再复用同一硬件预算。在 **Terminal A** 前台从 exact v3.1 artifact 启动一个全新 candidate generation，使用不同端口与 control file：

```text
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm serve --config configs/releases/v3.1/reliable-pd.yaml --host 127.0.0.1 --port 8310 --control-file out/v3.1-hw/candidate.control.json --capture out/v3.1-hw/candidate
```

在 **Terminal B** wait-ready、发流量、执行运维/资格演练并显式 shutdown：

```text
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm server wait-ready --control-file out/v3.1-hw/candidate.control.json --timeout-s 600
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm bench --endpoint http://127.0.0.1:8310 --workload fixtures/v3.1/reliability-smoke.jsonl --output out/v3.1-hw/candidate-bench
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm ops drain --target decode-group-0 --deadline 120s --evidence out/v3.1-hw/drain-0
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm ops replace --target decode-group-0 --expected-generation 7 --evidence out/v3.1-hw/replace-0
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm qualify reliability --profile qualification/v3.1-release.yaml --output release/v3.1.0/qualification
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm ops diagnostics --output out/v3.1-hw/diagnostics
python scripts/in_env.py --manifest out/v3.1-hw/target-toolchain.json -- python -m illm server shutdown --control-file out/v3.1-hw/candidate.control.json --deadline-s 180
```

两条前台 `serve` 绝不能串在同一个 Terminal A；每个阶段均由 Terminal B 显式 shutdown，即使 bench/qualification 失败也不跳过清理。upgrade drill、reference 与 candidate 是三个串行、资源归零后才切换的阶段；drill 的 state/evidence identity 不得复用或修改 candidate control file。source/target ToolchainManifest、两个 wheel digest、共同 benchmark client digest、不同端口/control file、A/B transcript、退出码、固定预算与 shutdown 资源终态全部进入 qualification evidence；只更换 config 而仍运行 v3.1 binary 不能冒充 v3.0 reference。上述接口面向本地/单节点多进程 runtime，可由外部进程管理器调用，但不依赖或实现 Kubernetes controller。

#### 2.2.1 Conditional `v1.3-merged` qualification

只有基础 `reliable-redundant-soak-v1`、`rolling-upgrade-rollback-v1` 与 `security-release-v1` 在同一 candidate identity 上均为 `pass`，且 branch manifest 显式选择 `v1.3-merged-functional-reliability-v1` 时，才运行本段。先验证 content-addressed functional identity，然后在已归零的同一硬件预算上由 **Terminal A** 启动独立前台 generation：

```text

```

## 3. Scope

### 3.1 本版本新增

V3.1 的**唯一主要复杂度**是 **durable operational change safety**：任何会改变运行中 deployment 的操作，都必须可持久恢复、可 fencing、可验证、可回滚。lifecycle、journal、相邻版本升级、capacity、安全边界与 qualification 是这个目标不可拆开的资格 gates，不是六项可任选功能，也不新增推理算法、模型语义或 data-path 能力。它们可以按 slice 学习，但正式资格缺少任一 gate 都必须 fail closed。

新手按每周 10～15 小时应为本版预留 **8～14 周**，且不含稀缺硬件排队与额外 72 小时 LTS promotion 窗口；估算口径见 [README 的完整版本列车](../README.md#2-完整版本列车)。

- 稳定的 service lifecycle：`STARTING/WARMING/READY/DRAINING/QUIESCED/STOPPING/STOPPED/UNHEALTHY/REPLACING`，每次启动使用新 generation。
- readiness gate：model/weight/config/protocol、MemoryPlan、KV/graph/transfer pool、dependency health、warmup 和安全前置全部通过才接流量。
- 有界 drain：先原子关闭 admission，再完成/显式终结 active 请求与 ticket，最后等待 fence/lease 回收并进入 QUIESCED。
- supervisor 驱动的 group/service replacement；replacement 冷启动、warm、canary 成功后才进入 routing set，旧 generation 消息被 fencing。
- N 与 N-1 相邻版本协议协商、config migration、滚动升级、canary、暂停、resume 和 rollback drill。
- 兼容域：会改变 model/KV layout/TP mapping 的升级必须整域 drain + cold rebuild，禁止跨域 live KV migration。
- reliability qualification：chaos、24 小时 soak、过载/恢复、资源漂移、故障检测/替换和滚动升级/回滚。
- 版本化 capacity plan、headroom、水位、admission、degraded mode、告警阈值和 deployment class。
- 最小安全边界：监听/管理面隔离、静态 bearer 或受信反向代理认证、TLS 边界声明、资源上限、输入/路径校验、模型 digest、capture redaction/retention、SBOM/依赖/secret scan。
- 运维 evidence bundle、diagnostics snapshot、runbooks、stable support matrix 与有条件 LTS policy。
- 可选 `v1.3-merged` 只增加对已存在 advanced-generation branch 的可靠性组合资格与 encrypted R2 capture tier；它不是基础依赖、不改变默认 data path，也不新增推理算法。

### 3.2 本版本保持不变

- V3.0 的推理语义、模型支持范围、Attention/KV/Sampling contract、P/D ticket 事务、TP/DP group 规则和 unified fallback。
- accepted request 唯一 terminal、已输出 stream 不透明 retry、GPU fence 前不释放/复用资源的硬不变量。
- 等预算 benchmark、capture 隐私默认值、R0/R1 事实边界和 telemetry 不得阻塞推理。
- 所有高级 backend 仍只在各自 support matrix 内有效；V3.1 不把实验性组合自动提升为 stable。

## 4. Non-goals

- Kubernetes operator、Helm/chart 管理、云厂商 autoscaling、服务网格、跨区域复制或通用部署平台。
- 计费、结算、商业 SLA、租户身份生命周期、RBAC/IAM 平台、复杂 quota marketplace 或审计合规认证。
- 任意版本跳跃的零停机升级、breaking KV layout 的 live migration、跨 TP degree reshard 或持久化 in-flight request checkpoint。
- 对单副本/单链 deployment 承诺无中断升级或故障无感；零中断前提必须是 support matrix 声明的冗余 deployment class。
- 网络层 exactly-once：客户端断线、代理重试和重复提交需要调用方 idempotency；引擎只保证每个 accepted internal request ID 唯一 terminal。
- 引入新的推理算法、模型架构、量化、多模态、MoE 或分布式策略。
- 全功能 WAF、证书颁发机构、密钥管理服务或 sandbox；本版本只建立最小安全边界和集成点。

### 5.3 数据流与状态迁移

```text
Worker lifecycle:
STOPPED → STARTING → WARMING → READY → DRAINING → QUIESCED → STOPPING → STOPPED
                 │        │          │
                 └────────┴──────────┴→ UNHEALTHY → REPLACING → STARTING(new generation)

Graceful rollout for one compatibility domain:
preflight → start canary(N) → warm/readiness → limited traffic/guardrail
→ close admission to target(N-1) → drain → quiesce → stop
→ start replacement(N) → warm/readiness → restore traffic → observe
→ repeat or pause → finalize

Rollback:
guardrail fail → stop new N admissions → drain N → restore pinned N-1 artifact/config
→ warm/readiness → canary → restore traffic → preserve all evidence
```

补充合法故障/中止边：`STARTING/WARMING/READY/DRAINING/QUIESCED/STOPPING/REPLACING → UNHEALTHY`；`REPLACING` 只有取得新 generation 后才能进入 `STARTING`，预算耗尽回 `UNHEALTHY`；`STOPPING` 只有确认进程退出与 lease/fence 清空后进入 `STOPPED`。drain 在 stop 前被显式 abort 时不得直接回 READY，而是先等所有 admission lease 决议、递增 `readiness_epoch`，经 `WARMING → READY` 和 canary 重新加入；状态未知时 safe-pause/fail-stop。

Drain contract：

1. 每个 admission RPC 携带 `(target_generation, readiness_epoch, admission_attempt_id)`。权威 admission transaction 只允许在 `READY` 且 epoch 完全相同时，把 `PENDING` 原子转换为 `ACCEPTED_BUNDLE` 或 `REJECTED/FENCED_NO_ACCEPT`：unified 路径的 accepted transaction 同时提交 `AdmissionLease + request.accepted`；P/D 路径必须原样继承 V3.0，同时提交 `AdmissionLease + FutureDecodeCredit + request.accepted`。不存在先 `RESERVED`、稍后再发 accepted 的窗口。
2. coordinator 先用持久 `MutationLease` 以 `(target_id, expected_generation, drain_id)` CAS 将 target 置为 DRAINING 并递增 `readiness_epoch`；target 从此拒绝旧/新 epoch 的未决 admission。
3. router 从 routing membership 撤销该 generation，发布并确认新的 routing epoch；随后等待撤销前已发送的所有 admission attempt 得到 durable `ACCEPTED_BUNDLE` 或 `REJECTED/FENCED_NO_ACCEPT` 决议。`ACCEPTED_BUNDLE` 与 accepted mutation 已在同一 commit 中发生；其余状态被 epoch fence 永久禁止 accepted。**drain ack 只在这些决议和 membership 撤销均持久后返回，它就是“ack 后新 accepted=0”的线性化点。**
4. target 继续完成 ack 前已 accepted 请求与 transfer/collective；未开始的内部工作不得扩大资源承诺。deadline 到期时未输出请求按 policy cancel/fail，已输出 stream 发送 terminal error；所有 ticket/collective 仍按 fence contract 收尾。
5. active requests、AdmissionLease/AdmissionBundle、FutureDecodeCredit、tickets、non-cache leases 为 0，且 cache/graph pool 已按升级兼容性保留或丢弃后进入 QUIESCED。STOP/replace 使用新 generation；迟到旧 heartbeat、ack、ticket、output 被拒绝并计数。

Coordinator durability contract：

1. baseline 使用 checksum-protected SQLite WAL（或通过相同 fault suite 的 `OperationJournal` adapter），每个 mutation 在发副作用前先原子持久化 `operation_id, coordinator_epoch, target_generation, plan_digest, phase, command_id`；phase commit 到达声明的 durable boundary 后才能对外 ack。
2. `CoordinatorEpoch` 由 durable compare-and-swap 单调递增；同一兼容域同一时刻只有一个未过期 `MutationLease`。所有 supervisor/target mutation 都携带 epoch/lease，旧 coordinator 命令无条件拒绝。
3. restart 先读取 journal、验证 checksum/sequence、获取新 epoch/lease，再按 phase 重发幂等 command 或完成补偿；重复 operation ID 返回已有状态，不创建第二 replacement/stop/rollback。
4. journal 缺页、checksum 错、phase 含糊或 durable store 不可用时进入 `SAFE_PAUSED`：保持已知健康 data plane，但阻止新 rollout/drain/replacement mutation并告警；不得猜测继续。

升级兼容域由 model/spec/weights、runtime dtype、TP mapping、KV layout、transfer protocol 与 cache/graph identity 构成。任一 identity breaking change 要整域 drain；只添加可选 event/config 字段可相邻版本滚动。

## 6. Contracts

### 6.1 API/CLI contract

- generation API v1 在 v3.1.x 内 stable；patch release 不删除字段、不改变默认采样/错误/stream terminal 语义。弃用至少提前一个 minor release 并记录 replacement。
- health endpoints 分离：`/health/live` 仅进程；`/health/ready` 表示可安全 admission；`/health/status` 返回 bounded role/generation/version/dependency/capacity reason，不含 secret、prompt 或内部路径。
- admin API 与 public API 使用独立 listener；admin 默认 loopback，所有 mutation 要认证、带 operator request ID 并产生 audit event。
- `ops drain/replace/rollout/rollback` 必须幂等；重复相同 operation ID 返回既有状态。target generation 不匹配返回 conflict，不能作用于新进程。
- rollout plan 固定 source/target artifact digest、兼容域、batch、canary traffic、observation window、guardrails、abort/rollback action；运行中更改要新 plan/version。
- 客户端请求在 drain/replace 中仍遵守 429/503 与唯一 terminal contract；健康冗余存在时 router 可在 accepted 前重选，accepted 后不透明迁移已输出请求。
- diagnostics export 有大小/时长上限和 redaction profile；采集失败不阻塞推理，只将证据标为 incomplete。
- `illm release qualify` 对 optional profile 必须验证 `required_for_base=false`、exact identity、前置 profile pass digest、完整 shutdown/resource terminal 与 evidence digest，原子签发独立 `profile-result.json`；它不得改写基础 `manifest.json`、其他 profile result 或六轴聚合结果。

| 字段/对象 | 稳定性 | 兼容规则 |
|---|---|---|
| `config_schema_version` | stable | v3.1 reader 接受 v3.0/v3.1；迁移输出新文件并保存原 digest，不原地覆盖 |
| `service_protocol_range` | stable | 只支持 support matrix 中 N/N-1；双方 capability 交集为空不 ready |
| `SupportMatrix` | stable | 固定 deployment class、model/topology、GPU、driver/CUDA/NCCL、schema/protocol 与已验证 source/target 组合；未知组合 fail closed |
| `deployment_class` | stable | `development_single_chain` 或 `reliable_redundant`; 后者必须满足冗余与容量规则 |
| `lifecycle.drain_deadline/restart_budget` | stable | 有界且进入 rollout digest；restart budget 含窗口与最大次数 |
| `capacity_plan` | stable | model/topology/workload/SLO、每资源峰值/headroom/watermark、degraded capacity 和 evidence digest |
| `UpgradePlan` | stable | immutable source/target artifact/config/`SupportMatrix` digests、批次、canary、guardrails、abort/rollback；签署 evidence |
| `OperationJournal` | stable | append-only operation/phase/command/result records，checksum + monotonic sequence；durable adapter 未通过 kill-boundary suite 时不可用于 mutation |
| `CoordinatorEpoch` | stable | durable CAS 单调递增；所有 mutation command 必带，旧 epoch fail closed |
| `MutationLease` | stable | `(compatibility_domain,target_generation,coordinator_epoch,expiry)` 唯一；过期/冲突时 safe-pause，不并发写 |
| `security_policy` | stable | bind/admin/auth/TLS boundary、content capture、retention、model source；缺失关键字段 fail closed |
| `SupportPolicy` | stable | 引用 `SupportMatrix`，声明兼容窗口、LTS 起止、backport 类别和 EOL；release 后只可收紧安全边界或发新版本 |
| `ReleaseEvidenceManifest` | stable | 引用所有测试/raw/signature/SBOM；缺件标 incomplete，不可宣称 qualified |
| `V13MergedReliabilityIdentityV1` | experimental | functional profile 的 content-addressed exact identity；任何 candidate/upstream-generation/runtime/topology/model/speculation/workload digest 改变都必须新 manifest 与新结果 |
| `EncryptedR2ReliabilityCaptureManifestV1` | experimental | 只能引用同 identity 的 functional `pass` result；固定 `replay_capability=R2`、`content_mode=encrypted_tokens`、payload/encryption/retention/delete 与 expected execution digest |
| optional profile `profile-result.json` | experimental | 两个 profile 各自保存 profile ID、`required_for_base=false`、identity/evidence/prerequisite digests、`pass/fail/invalid/not_applicable` outcome 与 reason；一个结果不得覆盖或推导另一个 |
| `LtsPromotionAttestationV1` | stable | detached、append-only；只在 promotion gate 通过后签发；包含 candidate manifest/artifact、ReleaseEvidenceManifest、SupportMatrix、SupportPolicy、72h qualification 的 exact digest，以及 issuer/key ID、decision time、LTS window 与签名；不得修改被引用对象 |

`V13MergedReliabilityIdentityV1` 至少绑定 exact v3.1 candidate wheel/release/config/lock/toolchain、`SupportMatrix`、deployment/topology/protocol、model/tokenizer/weights/KV layout，以及上游 `v1.3-merged-functional-tp-v1`、`v1.3-merged-functional-dp-v1`、`v1.3-merged-functional-pd-v1` 三个 `pass` result/digest；advanced-generation identity 必含 SamplingSpec v2、GrammarSpec、`SpecTxnV1`、target/draft、RNG draw registry、leader commit 和 draft-target KV contract digest；资格 identity 还必须固定 workload/seed、fault/soak profile、capacity plan 和 base `reliable-redundant-soak-v1`、`rolling-upgrade-rollback-v1`、`security-release-v1` 三个 required profile result digest。任一引用缺失、非 pass、digest 漂移或 identity 跨 compatibility domain 时，functional profile 为 `invalid`，不能启动 optional generation。

`EncryptedR2ReliabilityCaptureManifestV1` 必须引用上述 functional identity 与其 exact `pass` result digest，并额外固定 capture/event/input schema、`replay_capability=R2`、`content_mode=encrypted_tokens`、被捕获的 input/token/p/q/logits/RNG/grammar/transaction 字段集、加密算法/key ID（不记录 key）、访问主体、最长 24 小时 retention、verified deletion procedure、fixture digest 与 expected execution digest。默认 metadata-only/equality-only 仍最高 R1；functional pass 绝不隐式升级 replay capability。

两个 `profile-result.json` 是正交事实：R2 只有在 functional result 已 pass 且 identity digest exact match 后才能从 `not_applicable` 进入实际运行结果；R2 fail/invalid 只撤销 R2 claim，functional 结果保持不变。branch 未合入时 functional 为 `not_applicable/optional_branch_not_merged`、R2 保持 `not_applicable/opt_in_profile_not_selected`；branch 已合入但 functional lane 未选择时两者均为 `not_applicable/opt_in_profile_not_selected`；functional 已选择但 encrypted tier 未选择时只有 R2 保持该状态。release verifier 必须从基础资格聚合中排除 `required_for_base=false`，因此 optional not-applicable/fail 不阻断 base release，但 `SupportMatrix` 不得声明对应能力。

### 6.3 Event/capture/replay contract

- 新增 `service.lifecycle_changed`、`service.readiness_changed`、`service.generation_fenced`、`admission.decision_resolved`、`engine.draining/quiesced`、`operation.phase_durable/safe_paused`、`worker.replacement_started/completed/failed`、`rollout.started/canary_passed/paused/rolled_back/completed`、`capacity.watermark_crossed/recovered`、`security.policy_rejected`；conditional lane 另记录 `qualification.optional_profile_started/completed`、`capture.encrypted_r2_started/finalized/deleted` 与 `replay.r2_execution_completed`。
- ops event 必含 immutable `operation_id`、actor kind（不记录 credential）、target/generation、source/target version/config digest、reason、deadline 和 terminal status。
- 每次 drain/rollout/chaos/soak 生成独立 capture session 与 evidence manifest；捕获缺口、时钟不确定性、被丢事件和无效 run 原因显式记录。
- R0/R1 支持读取当前及 support matrix 声明的两个先前 event schema；migration 保留原 event ID/producer seq 和未知字段，不伪造缺失事实。
- R1 reducer 按 authority-local mutation sequence、operation journal phase 与 causal command/result link 重建 service lifecycle、routing membership、admission lease、operation、request terminal、ticket 和 resource digest；跨 producer timestamp 只用于展示，不决定 mutation 顺序。optional encrypted R2 只能在 exact captured inputs 上重执行数值 forward、Sampling/Grammar/`SpecTxnV1` 与 commit digest；R2 **不能**复现真实 worker crash timing、网络调度、跨进程 wall-clock race 或 injection 到达顺序，这些结论只能引用 measured injection manifest 与 R0/R1 因果事件。本版不声明 R3 replay capability，容量/rollout UI 的 what-if 只是 `estimated` 分析，不能以 R3 名义通过 capability check。
- metrics label 不含 request/operation ID；运维指标统一注册为 `illm.ops.service.state.v1`、`illm.ops.ready_replicas.v1`、`illm.ops.worker.replacement_total.v1`、`illm.ops.drain.active.v1`、`illm.ops.stale_generation_messages_total.v1`、`illm.ops.capacity.watermark.v1`、`illm.http.unexpected_5xx_total.v1`、`illm.request.terminal.accounting_gap.v1`，且只允许 registry 声明的低基数 attributes。

### 6.4 资源、并发与失败 contract

- `reliable_redundant` 至少有两条可承载 public 请求的 qualification path；P/D 可由两套完整 P/D chain 或一套 P/D + 具有声明容量的 unified fallback 构成。单链只属于 development class。
- capacity plan 对每 GPU/role/rank 保留至少 15% device-memory safety headroom（在固定 graph/pool 之后），稳态 qualification load 的瓶颈资源目标利用率不超过 70%；更高值需 ADR 和故障证据。
- admission 使用最小剩余 capacity 的服务作为整条 path 上限；不得因 aggregate 空闲而超卖某个 Decode KV/transfer/TP rank。
- drain ack 是 routing membership 撤销且全部 in-flight admission attempts 已原子决议为 `ACCEPTED_BUNDLE` 或 `REJECTED/FENCED_NO_ACCEPT` 的线性化点；P/D 决议必须包含 FutureDecodeCredit。此后 target/generation 新 accepted request 为 0。internal cleanup 可继续，deadline 强制终结不等于可提前释放，所有 device/collective/transfer fence 仍必须 resolve。
- supervisor 对同一 target generation 只启动一个 replacement operation；restart budget 默认 3 次/15 分钟，超过后保持 unhealthy、阻止 crash loop 并要求 operator decision。
- replacement 不恢复旧进程内 KV/ticket/graph；兼容 cache 可以保留只读 artifact，但必须重新验证 digest/ownership。in-flight 的安全 retry 仍服从 V3.0 状态规则。
- 在有冗余路径时，worker/service failure 被摘除后健康路径继续；若剩余 capacity 不足则 bounded 429/503，不牺牲 MemoryPlan 或 SLO guardrail 强接。
- readiness 需要连续两个独立 probe 周期并通过 warmup canary；liveness 不可替代 readiness。stale registry/heartbeat 超过阈值即停止 admission。
- 所有 control-plane 操作由 durable operation/command ID、`CoordinatorEpoch`、`MutationLease` 和 target generation 共同 fencing；旧消息、重复命令和 coordinator restart 不能产生第二 replacement、第二 terminal 或重复资源释放。journal 无法证明 phase 时只能 `SAFE_PAUSED`。

### 6.5 最小安全边界

- public/admin 默认 bind loopback 或显式 private interface。非 loopback public bind 必须设置 `external_access_ack`、请求认证，并声明“进程内 TLS”或“受信反向代理终止 TLS”；否则启动失败。
- admin listener 默认 loopback；远程 admin 必须双独立条件：认证 secret + TLS boundary。static bearer 仅是最小实现，secret 从环境变量或权限受控文件读取，禁止 CLI 参数、日志、capture 和 diagnostics 输出。
- 所有 request body、prompt/output token、queued token、并发连接、header、capture、diagnostics 和路径均有 hard limit；路径 canonicalize 后必须位于配置 root，拒绝 traversal/symlink escape。
- `trust_remote_code=false`；模型/config/weights 使用 allowlisted source 与固定 digest，loader 继续拒绝 missing/unexpected/duplicate tensor。artifact 校验失败不 ready。
- capture 默认 metadata-only，不记录原始 prompt/output；内容模式需显式开启、加密 at rest、配置最长 24 小时保留并产生 audit event。删除流程验证 index 与文件均不可再读。
- UI/API 的跨站来源、WebSocket 和 debug endpoint 默认关闭或同源；错误消息不泄漏 secret、绝对路径、prompt 或权重内容。
- release 生成 SBOM、依赖漏洞扫描、secret scan 和 license inventory；未解决 critical/high 安全问题阻断，例外必须有有期限的 ADR、缓解措施和 owner。
- 本安全边界不宣称强多租户隔离或合规认证；不可信租户代码/模型不得在同一进程安全域运行。

## 8. Correctness and Invariants

### 8.1 Golden/differential

- V3.0 client contract suite 对 v3.1 public API 全部通过；相同 model/config/sampling 的 stable data path 在 v3.0/v3.1 greedy token 100% 一致。
- v3.0 config 经 migrator 产生 canonical v3.1 config，语义 digest 与预期 golden 一致；原文件和 digest 保留，未知语义字段 fail closed。
- N/N-1 service protocol 的每个支持 pair 运行成功/错误/cancel/transfer/drain matrix；N/N-2 和 capability 无交集均在 readiness 前拒绝。
- 当前与两个先前 event schema fixture 可读且 R1 expected digest 一致；未知字段保留，enum/field number 不复用。
- drain/replace/rollout/rollback 开启与关闭时，非故障请求的 token/RNG/terminal 语义不变；control plane 不进入模型数值路径。
- 条件 functional fixture 在 drain/replace/rollout/rollback/worker-kill 下，与 exact upstream v1.3 oracle 比较 SamplingSpec v2 draw addresses、GrammarSpec state、`SpecTxnV1` commit/rollback、draft-target KV、token/terminal digest；encrypted R2 另对固定 capture 重执行并匹配 expected execution digest，二者不得共用 outcome。

### 8.2 Property/state invariants

- lifecycle transition 只按 §5.3 正常边、补充故障边和 drain-abort rewarm 边前进；每个 `(generation,readiness_epoch)` 最多一次 READY，每个 drain/stop operation 最多一个 terminal。
- drain ack 前 routing membership 已撤销且所有旧 epoch admission lease 均已决议；ack 后该 target/generation 新 accepted 为 0；QUIESCED 时 active request/admission lease/ticket/non-cache lease 为 0。
- 同一 operation ID 幂等；不同 operation 不能同时持有同 compatibility domain/target generation 的 mutation lease；durable journal phase 单调且 coordinator epoch 只增不减。
- registry 中 routing member 必须是当前 generation、READY、protocol compatible、capacity non-zero；任一条件失效后有界时间内摘除。
- 每个 accepted request 一个 terminal；rolling/chaos/restart 中 lost、duplicate、double-terminal 和 terminal-accounting gap 为 0。
- replacement 不继承未知 device state；stale generation message 不改变 request/ticket/service/resource 状态。
- queue/ticket/page/staging/host diagnostic buffer 均不超过 capacity plan；所有拒绝有稳定 reason code。
- evidence manifest 引用的每个 artifact 有 digest、命令、版本、时间、硬件和 complete/invalid 状态；invalid run 不计作 pass。
- optional R2 profile `pass` ⇒ 存在同 exact identity 的 functional `pass` result；functional/R2 identity、evidence 与 outcome digest 均独立且不可原地改写。未选择 profile 保持 `not_applicable`，不进入 base qualification 分母；R2 failure 不改变 functional result。

### 8.3 Failure/stress matrix

| 场景 | 注入方式 | 必须结果 | 禁止结果 |
|---|---|---|---|
| worker 在 READY 时退出 | 随机 kill rank/service | 5 秒目标检测内摘除；健康路径继续；bounded replacement | 新请求进入死 generation |
| drain 中请求很慢 | 固定长请求 + 短 deadline | deadline 后显式终结，fence 后 QUIESCED | 永久 drain、提前释放 |
| coordinator 在 rollout 中退出 | kill/restart control process | 从 operation journal 恢复或安全暂停；不重复 replacement | 跳过 canary/重复 stop |
| journal 每个 write/fsync 边界损坏/退出 | kill、truncate、checksum corruption | 可证明 phase 则幂等恢复；否则 SAFE_PAUSED 且健康 data plane 保持 | 猜测 phase、双 mutation、旧 coordinator 写入 |
| admission RPC 与 drain 并发 | barrier 控制 RPC 在 membership 撤销前后到达 | ack 等所有 lease 决议；ack 后 accepted=0 | late RPC 穿透 DRAINING |
| canary correctness/5xx 回归 | fault candidate backend | rollout 暂停并触发 rollback decision | 自动推进下一批 |
| rollback artifact/config 损坏 | checksum/compat 注入 | preflight 拒绝；保持当前健康版本或 fail safe | 停止全部健康容量后才发现 |
| heartbeat 延迟/旧 generation 消息 | reorder/replay control messages | stale counter 增长，状态不变 | 旧 worker 重新 ready |
| 200% 持续过载 | open-loop burst 60 分钟 | bounded 429、无 OOM/死锁，降载后恢复 | 无界 queue、collapse 后不恢复 |
| device OOM/NCCL/transfer 错误 | backend fault hooks | 可信性未知 group fail-stop、replacement、明确 terminal | 局部错误 KV 继续服务 |
| telemetry/evidence disk 满 | 限制 sink/disk quota | inference 继续，低优先级丢弃并告警/incomplete | data plane 被阻塞 |
| auth/path/model digest 攻击 | 无 token、traversal、超限、损坏 artifact | 401/403/413 或 startup fail closed，无敏感泄漏 | 访问 root 外文件/执行 remote code |

## 11. Compatibility and Migration

### 11.1 Compatibility matrix

| Artifact | 读取上一版本 | 写入格式 | Breaking 条件 | 迁移/降级 |
|---|:---:|---|---|---|
| config | 是（v3.0/v3.1） | v3.1 canonical | 删除/改语义、未知执行字段 | migrator 写新文件；保留 dual-compatible rollback config |
| public API/CLI | 是 | API v1、ops CLI v1 | generation API breaking 仅允许下一 major | v3.0 client contract suite；ops CLI 按 exact minor |
| service protocol | N/N-1 | 当前协议 + capability range | 无交集、N/N-2、breaking state/identity | preflight fail；整 compatibility domain drain |
| event/capture | 当前+前两个 schema | 当前 schema | 复用 field/enum、缺 migration | offline migrator/read adapter；不 down-convert 事实 |
| model/weight manifest | 是，exact identity | 当前 canonical manifest | model/spec/weights/dtype 改变 | 重新 load/warm；旧 cache/KV 不复用 |
| KV transfer/ticket | 仅 exact manifest 和支持协议 | 当前 journal/ticket | layout/TP/generation/protocol breaking | drain ticket、cold rebuild；不恢复 in-flight |
| cache/graph artifact | 仅 identity exact | 当前 role/topology/versioned format | binary/backend/layout/GraphKey 不兼容 | disposable；重新 warm，不阻断 rollback |
| release evidence | 是，只读 | v3.1 manifest | 缺 digest/command/hardware/complete status | 标 incomplete，不能签署 qualification |
| LTS promotion | 不适用 | detached signed `LtsPromotionAttestationV1` | 任一引用 digest、签名、issuer policy 或 qualification gate 不匹配 | 保持 candidate；不得改写 manifest 补救 |
| optional v1.3 functional reliability | 否 | 独立 `V13MergedReliabilityIdentityV1` + profile result | candidate/upstream merged result、SamplingSpec/GrammarSpec/`SpecTxnV1`/draft-target KV/topology/workload 任一 digest 改变 | 关闭 optional generation并标 unsupported；base V3.1 保持不变 |
| optional encrypted R2 tier | 否 | 独立 `EncryptedR2ReliabilityCaptureManifestV1` + profile result | functional pass/identity、capture capability/content/encryption/retention 或 execution digest 改变 | 停止敏感 capture并验证删除，降回 R1；functional/base outcome 不变 |

支持窗口与稳定性规则：

| Surface | v3.1 承诺 | 不支持/限制 |
|---|---|---|
| API v1 | v3.1.x patch 向后兼容；弃用至少提前一个 minor | major 才可 breaking |
| config | 读取 v3.0 和 v3.1；只写 v3.1 | 不原地降级写回 v3.0 |
| mixed-version runtime | v3.1 与 v3.0 仅在 capability matrix 声明的滚动窗口互通 | 不允许长期混跑或跨两 minor/major |
| capture reader | 当前及前两个 schema | 不保证旧 binary 读取新 ops event |
| hardware/software | 仅 `supported-matrix.md` 中 GPU/driver/CUDA/NCCL/OS/backend | 未列组合为 experimental/unsupported |
| reliable deployment | 至少两条 qualification path 与足够 degraded capacity | 单链无零中断/故障可用性承诺 |

LTS policy：`v3.1.x` 是首个 LTS candidate。candidate package、`manifest.json`、`ReleaseEvidenceManifest`、`SupportMatrix` 与 `SupportPolicy` 一经发布即 content-addressed immutable，初始状态只能是 candidate。只有 §12.3 的 72 小时 LTS qualification 通过、无未豁免 critical/high 安全或 correctness 问题、support matrix 与 rollback evidence 完整后，promotion authority 才签发 detached `LtsPromotionAttestationV1`；消费者只有在校验签名、issuer policy 及全部引用 digest 后才能显示 LTS。禁止把 `lts=true` 回写 candidate manifest、覆盖 evidence 或移动 tag 来伪造 promotion；失败时不签发 attestation并保留 candidate，后续补测必须形成新 evidence manifest 与新 attestation。撤销/EOL 也以新的 signed attestation/policy artifact 追加，不修改历史证明。LTS 维护窗口为 attestation 声明的起止时间，首个计划窗口为 `v3.1.0` 发布后 12 个月；维护 critical security、data/correctness corruption 和 high reliability bug，性能增强不默认 backport。每次 patch 仍需 compatibility、upgrade/rollback、24 小时缩减 qualification；项目只维护一个 active LTS line，EOL 至少提前 90 天写入 support policy。

### 11.2 Rollback

1. rollout 前必须验证并保留 source binary、dependency lock、config、model/weight、support matrix 和 evidence digest；rollback 不依赖在线下载。
2. canary/guardrail 失败时停止对 candidate 新 admission，保存 capture/diagnostics，按 compatibility domain drain candidate。
3. 恢复 dual-compatible source config 与固定旧 binary，冷建所有 version/layout-bound cache/graph/KV，完成 warmup/readiness 后有限 canary。
4. 健康 source capacity 恢复后再扩流量；所有 candidate 旧 generation 消息被 fencing。若旧版本本身不 ready，保持当前健康容量并人工处置，禁止循环翻转。
5. 正常冗余 rollout/rollback 的目标为无升级导致的 accepted-request failure；强制 deadline case 必须显式 terminal 并进入 evidence/error budget。
6. schema/model/layout breaking change 不允许使用滚动 rollback，必须维护窗口整域 drain；preflight 必须在停止健康容量前指出这一点。
7. optional functional rollback 先停止新的 `SpecTxnV1` admission、drain/fence 全部 transaction，再回基础 V3.1 path；只撤销 encrypted R2 时停止敏感 capture、销毁 key handle、按 manifest 验证保留/删除并降为 R1。两者都不得改写历史 profile result，也不得触发基础 binary/config rollback。

## 12. Definition of Done

### 12.1 Learning Gate (`learning_complete`)

- [ ] §1.3/§2.1 的 generation fencing、drain race 与每个 durable boundary journal-recovery CPU simulator 全部通过。

- [ ] `OperationJournal` 在每个 write/fsync/phase-ack 边界执行 kill/restart，并覆盖 truncate/checksum/旧 coordinator 竞态：要么从唯一 durable phase 幂等恢复，要么 SAFE_PAUSED；重复 mutation、旧 epoch 写入和双 replacement 均为 0。
- [ ] 至少 100 次 drain（包含长请求、cancel、transfer、collective 和 delayed admission RPC）：drain ack 前 membership 已撤销且 admission lease 全部决议；ack 后 target 新 accepted 为 0；99.9% 请求在 qualification deadline 内自然完成；其余全部显式 terminal；最终 active admission lease/ticket/non-cache lease 为 0。

- [ ] 24 小时且至少 100,000 accepted requests 的 steady mixed soak：lost/duplicate/double-terminal 为 0，非注入 unexpected 5xx≤0.1%，request terminal accounting=100%，进程 crash/deadlock=0。

- [ ] 至少 200 个 chaos cases 覆盖 worker exit、NCCL/transfer async error、heartbeat、stale generation、coordinator restart、disk/exporter、OOM/cancel race；所有 case 满足唯一 terminal、有界恢复或明确 fail-safe。
- [ ] 200% qualification offered load 持续 60 分钟无 OOM/deadlock/容量越界；预期 overload 由 429/503 表达；降到 70% 后 10 分钟内 queue depth、`illm.server.ttft.request_weighted.p99.v1` 与 `illm.server.itl.token_weighted.p99.v1` 恢复到同 load baseline ±15%。
- [ ] 每个 supported topology 有 versioned capacity plan：device headroom≥15%、hard watermark/queue/credit/restart budget 已验证；degraded capacity 不足时 fail closed。
- [ ] §10 reliability overhead success rule 达成，correctness 与 security/health/evidence 功能未为性能关闭。
- [ ] §6.5 安全 negative tests 全过；未认证 admin/public、path traversal、超限、损坏 model/artifact 均被拒绝；SBOM、secret/license/dependency scans 无未豁免 critical/high。
- [ ] 至少 10 次 canary-failure rollback drill 在 `2 × cold_start_p95 + 120 秒` 内恢复已知良好 ready capacity，且没有重复输出/旧 generation 复活。

## 13. Known Limitations

- 可靠性承诺仅覆盖 `supported-matrix.md` 的硬件、driver/CUDA/NCCL、模型、拓扑、backend 与 deployment class；其他组合没有隐含支持。
- 单节点仍是物理故障域；即使有多 replica，也不保证节点断电、整机 kernel panic 或机房故障时可用。
- 单链 development deployment 不具备零中断 upgrade/worker failure 能力，只保证显式失败、资源安全和可恢复启动。
- 不持久化 in-flight KV/request，worker replacement 可能重做尚未输出请求；已输出 stream 在 worker failure 时仍会显式失败。
- 静态 bearer/受信代理只是最小安全边界，不是强多租户 IAM；不可信租户、模型代码或插件必须使用外部隔离。
- LTS 是版本维护和兼容承诺，不是商业响应时间/SLA；资源、维护者和 EOL 状态必须在 support policy 中透明更新。
- encrypted R2 只在固定 exact inputs 上证明 numerical/transaction re-execution；它不能复现真实 crash timing、network scheduling 或跨进程 race，也不能替代 24/72 小时 chaos/soak evidence。
- breaking model/KV/TP identity 仍需整 compatibility domain drain，不能滚动 live migrate。
- 自动扩缩、计费、Kubernetes、跨区域容灾和通用平台能力明确不在项目终点定义中。

### 13.1 下一版本输入

- 后续 patch 只能修复 correctness/security/reliability 与 support matrix 内回归，不得引入 breaking contract。
- 新 major 版本需从真实 24/72 小时 evidence、用户 workload、未解决 limitation 和 ADR 出发；不能仅因技术新颖扩大范围。
- 若未来进入多节点高可用，应新建 SPEC，明确节点/网络故障域、持久状态、quorum、跨节点 capacity 和安全模型，而不是把 V3.1 的单节点承诺外推。
