## 1. 本版本学习目标

### 1.1 必须掌握

- 能够区分 metrics、canonical event、state delta、checkpoint、derived trace 与 profiler 数据，解释各自的事实边界。
- 能够实现单调 `state_seq_no`、纯 state reducer、周期 checkpoint 和 canonical `EngineStateDigest`，并定位首次 replay divergence。
- 能够解释 R0 Event Playback 与 R1 Control-plane Replay 的能力差异，以及为何没有 token IDs/KV tensor 仍不能称为 R2。
- 能够用 monotonic CPU/CUDA clock domain、flow/link 和多对多关系表达 `Request → Step → Batch → KV` 因果，而不是伪造父子 span。
- 能够从记录时生成的 `DecisionRecord` 解释 selected/deferred/preempted/evicted；UI 不重新运行 scheduler。
- 能够设计 bounded telemetry/capture、critical-event策略、drop/incomplete标记、隐私模式、checksum与保留期。
- 能够把同一事实模型转换为学习视图和诊断视图，并明确 `measured/derived/estimated/unknown/dropped/incomplete`。

### 1.2 建议先修

- 已完成 v0.7 continuous batching、paged KV、preemption、chunked prefill、radix prefix cache 和完整事务事件。
- 理解 event sourcing、reducer、snapshot/checkpoint、canonical serialization、hash/digest、schema evolution。
- 熟悉 Web UI state management、时间轴、多对多关联、基本 Playwright/screenshot测试。

### 1.3 进入门槛与预热实验

- 预计用时 45～60 分钟；用离线 CPU bundle/reducer 完成，三视图只读取同一 canonical state。
- 门槛：v0.7 的 page/preemption/chunk/prefix critical events 通过完整性审计，四字段 cache ownership 不再使用 generic refcount。
- 预热 A：手工从 1 个 checkpoint 顺序应用 5 个 toy deltas，并在每步重算 canonical digest。
- 预热 B：删除、重复、交换一个 delta，分别确认 gap、duplicate、out-of-order 能在首个坏序号 fail closed。
- 预热 C：把一个 request 同时链接到多个 step/batch/page，验证 UI 不能用错误的单父子 span 表达。
- 预热 D：列出 R0、R1、R2、R3 各自所需事实；无法说清能力边界时不得开始 Web 页面实现。

### 1.4 Teach-back 产物

- `release/v0.8.0/teach-back.md`：从一个 repeated-prefix + preemption capture 出发，在三个页面间追踪同一请求，说明每个视觉元素来自哪个 canonical event/delta，并演示损坏一个 delta 后 reducer 如何在首个不一致 step 报告结构化路径。

## 3. Scope

### 3.1 本版本新增

- Capture Bundle v1 manifest、文件清单、checksum、privacy/replay capability和schema compatibility policy。
- canonical `StateDeltaV1`、safe-boundary `EngineCheckpointV1`、每step `EngineStateDigestV1`和pure R1 reducer。
- R0 trace播放、R1 state replay、首次digest divergence结构化diff；超能力模式fail closed。
- bounded capture budget、critical/noncritical event分类、truncation/incomplete/non-replayable行为。
- Guided Request Story：请求阶段、token timeline、static module/shape摘要和证据解释。
- Scheduler Lab：queue lanes、request×step矩阵、step/batch card、DecisionRecord和budget。
- KV Cache Explorer：page grid/page table、radix tree、四字段ownership、LRU/eviction/preemption与time scrubber。
- 三入口共享timestamp/state cursor与request/step/batch/page/radix因果跳转；Chrome Trace JSON/静态HTML fallback。

### 3.2 本版本保持不变

- v0.7同步Engine Core、调度policy、AttentionPlan、paged KV/preemption/chunk/prefix语义和feature-off oracle。
- `SupportedModelSpec`、WeightLoadManifest、SamplingSpec/per-request RNG、MemoryPlan和terminal/error contract。
- canonical events由domain/core在自然事务中产生；observability、replay与web只消费，不修改在线请求。
- default privacy不保存prompt/output/token IDs，metrics不使用request/tenant高基数labels。

### 3.3 Feature flags 与 fallback

## 4. Non-goals

- R2 Numerical Re-execution、保存可执行input token IDs/private input、重跑模型或跨backend数值比较。
- R3 Counterfactual What-if、离线重新运行scheduler/cache policy或用估计结果替代真实执行。
- live WebSocket生产观测、多人协作、远程capture中心或云端存储。
- 独立完整Model Explorer、Compiler/GPU/roofline、Compare Runs高级页；只在Guided Story中提供静态module/shape摘要。
- 改变v0.7调度、prefix、chunk、allocator或attention行为；为UI新增隐藏决策逻辑。
- Protobuf最终schema冻结、Rust/TypeScript跨语言binary event生产；V0仍使用versioned typed JSONL/JSON编码。
- M7 persistent input、compile/CUDA Graph、overlap、custom kernel或任何“为了展示”实施的性能优化。
- OpenAI-compatible HTTP稳定化、生产鉴权/计费、TP/DP/PD。

任何新增需求若改变以上 Non-goals、公开契约或 DoD，必须通过 spec amendment 或 ADR，而不是直接扩大 Issue。

## 5. Architecture Delta

### 5.1 相对上一版本的变化

```text
v0.7 Engine Core ── canonical events ──→ R0 inspector/static evidence

v0.8 Engine Core
  ├─ canonical observational events ──────────────┐
  └─ ordered StateDelta + periodic Checkpoint ───┤
                                                  ▼
                                      checksummed Capture Bundle
                                       ├─ R0 Event Player
                                       ├─ pure R1 State Reducer
                                       ├─ Chrome Trace exporter
                                       └─ Query/View Model API
                                             ├─ Guided Request Story
                                             ├─ Scheduler Lab
                                             └─ KV Cache Explorer
```

### 5.2 新增或修改的模块

| 模块 | 变化 | 责任边界 | 禁止事项 |
|---|---|---|---|
| `observability.schema` | change | canonical envelope、critical分类、JSON Schema/TS生成 | 引用Web组件或可变engine对象 |
| `capture` | change | safe-boundary checkpoint、delta/event写入、quota/checksum/manifest | 阻塞hot path、保存未opt-in敏感内容 |
| `replay.r0` | change | 验证、排序、播放canonical events | 推测缺失状态或重跑逻辑 |
| `replay.r1` | add | 从checkpoint纯应用deltas、digest校验与structured diff | 调用online scheduler、allocator或model |
| `replay.query` | add | 将reduced states/events索引为只读view model | 创造新的事实或修改bundle |
| `web` | add | 三页面、共享cursor/filter/causal navigation | 读取Python内部对象、复制scheduler/reducer逻辑 |
| `trace_export` | add | 从canonical events派生Chrome Trace | 成为事实源或混算CPU/GPU clock |
| `retention` | add | capture大小/时长/过期提示和安全清理manifest | 无提示删除或占满磁盘 |

### 5.3 数据流与状态迁移

R1 capture只在同步engine的scheduler commit安全边界启动；若用户在step中请求capture，系统等到下一边界建立完整checkpoint。之后每个会改变控制面状态的command生成一个有全序的delta：

```text
EngineCheckpointV1{at_state_seq_no, canonical_state, digest}
  → StateDeltaV1{
       state_seq_no, step_id, command_id, mutation_kind,
       expected_pre_digest, bounded_typed_payload, post_digest
    }
  → pure reduce(previous_state, delta)
  → canonicalize + EngineStateDigestV1
  → compare online post_digest
  → periodic checkpoint every N committed scheduler steps
```

observational event可拥有producer-local sequence和timestamp；state mutation的权威顺序只由`state_seq_no`决定，不用timestamp猜顺序。UI时间游标映射到“不晚于timestamp的最大已commit state_seq_no”，并保留同一时刻的request/batch多对多links。

## 6. Contracts

### 6.1 API/CLI contract

- `illm replay CAPTURE --mode trace`验证manifest/checksum/schema后播放R0；局部非关键事件缺失时显示gap，不自动升级能力。
- `--mode state --assert-state-digest`要求R1 manifest、初始checkpoint、连续state deltas和全部step digests；任一缺失直接失败并报告path/seq/expected/actual。
- `--mode execute`和`--mode what-if`在v0.8恒为unsupported，错误列出R2/R3需要的input token IDs、model/backend/RNG或policy simulation数据。
- `illm ui --capture ... --offline`只读打开bundle，不写回或修复；损坏bundle可在quarantine模式查看已验证R0片段，但R1控件禁用。
- UI/CLI每个页面/输出固定显示：bundle id、engine/model digest、最高replay capability、privacy mode、drop/truncated/incomplete、schema reader兼容性。
- `request_id/batch_id/step_id/page_id/radix_node_id`是独立filter/link，不构造严格父子树；timestamp是主时间游标，state_seq是控制面状态游标。
- capture开始/结束不改变scheduler选择、RNG、KV semantics或terminal；无法保证时必须拒绝R1 capture并保留普通推理。

### 6.2 Config/manifest contract

| 字段/对象 | 稳定性 | 兼容规则 |
|---|---|---|
| `capture_bundle_version=1` | `format_frozen_for_v0` | reader按manifest文件/encoding读取；未知major fail closed，未知optional文件可忽略并显示 |
| `event_schema_version=1` | `candidate` | envelope/required control payload 已进入 V1.0 候选；只 additive 演进，enum/code不复用；breaking语义升major；generated schema为唯一UI输入契约 |
| `StateDeltaV1` | `format_frozen_for_v0` | state_seq严格+1、pre/post digest必填、mutation kind有typed payload |
| `EngineCheckpointV1` | `format_frozen_for_v0` | 仅safe boundary生成；包含完整canonical control state与schema/config versions |
| `EngineStateDigestV1` | `format_frozen_for_v0` | canonical排序/数字编码/version固定；字段集改变必须新digest version |
| `replay_capability` | `candidate` | manifest显式`R0`或`R1`；不从文件猜测；`non_replayable`可降低实际能力 |
| `MetricRegistryV1` | `candidate` | 继承 V0.2 fully-qualified IDs 及其 boundary/单位/分母/weighting/failure 语义；V0.8 只升 candidate，V1.0 才 stable；语义变化必须新 ID |
| capture quotas/retention | `candidate` | safety 字段 bytes/sec、ring bytes、duration、bundle bytes、overflow、retention days 均必填 |
| `input_capture.mode` | `candidate` | privacy contract；v0.8 允许 metadata_only/equality_only；不保存可还原 token 内容 |
| `DistributionArtifactManifestV1` | `candidate` | `dist/artifact-manifest.json` 固定 exact wheel filename/version/SHA-256、lock digest、build provenance、Python tag 与 signature identity；bootstrap 在安装/项目导入前校验 checksums 与 detached signature，未知、缺失或篡改均 fail closed |

### 6.3 Event/capture/replay contract

- canonical event仍使用v0.7 typed JSONL schema v1；`events`是观测事实源，`trace.json/metrics/view indexes`均为派生物。
- R1 canonical control state至少覆盖：policy/config/snapshot版本；request状态/queue顺序/length/chunk progress/`next_output_position`/`rng_draws_consumed`/committed counter-address digest/terminal；current step/batch membership；allocator page states/valid counts/page tables；prefix nodes/edges/extents以及`request_lease_count`、`inflight_reader_writer_count`、`cache_indexed`、`cache_owner`、LRU；MemoryPlan/layout digest。
- R1不保存K/V tensor、logits、prompt/output token IDs，不能证明数值等价。radix token edge使用capture-local opaque identity与长度，仅重放当时mutation，不重新执行match。
- state-changing command在online commit时同步取得`state_seq_no`和小型typed delta；序列化/压缩可异步。delta进入有界critical queue失败时停止R1 capture、产生`CaptureTruncated`并标non-replayable，不能丢后继续声称R1。
- reducer从最近不晚于目标cursor的checkpoint开始，按state_seq应用delta并逐项比较pre/post digest；首次不一致报告如`requests[req-7].state`、`pages[12].valid_tokens`、`prefix.extents[e4].request_lease_count`或`prefix.extents[e4].cache_owner`。
- checkpoint和digest canonicalization排除timestamp、进程地址、Python hash/random iteration order；所有map/set稳定排序，整数/enum编码固定。
- span/event duration只在同clock domain计算；CPU/GPU flow通过clock snapshot与uncertainty展示，禁止直接相减得虚假duration。
- 默认metadata_only不保存文本；equality_only使用capture-local keyed opaque ID，仍提示长度/重复模式泄露。密钥不与bundle同存。

### 6.4 资源、并发与失败 contract

- 每个profile声明`max_event_bytes_per_sec`、`ring_buffer_bytes`、`max_capture_duration`、`max_bundle_bytes`、sampling、overflow和retention；达到上限先停止engine深度capture并显式truncated。
- inference hot path不格式化字符串、不做文件IO、不获取全局export锁；typed delta/event进入bounded queue，consumer批量写。
- terminal、scheduler commit/rollback、allocator reservation/write/release、preemption、prefix mutation/eviction是R1-critical；kernel细节、UI hints等可采样。
- exporter stall/磁盘满不使inference失败；普通metrics可drop并计数，R1 critical写入失败立即将bundle降为non-replayable并停止后续R1声明。
- reader限制解压后总bytes、单event大小、集合长度和递归深度；checksum/schema错误不执行bundle内代码或打开外部路径。
- UI只消费只读query model，所有字符串转义；capture中的路径不得越出bundle根目录。
- capture结束以两阶段finalize：停止接收→flush/校验序列→写manifest/checksums到临时名→原子publish。异常目录保持`incomplete`且不可被误认为成功bundle。

## 8. Correctness and Invariants

### 8.1 Golden/differential

- 对固定v0.7 fixture，同时保存online state snapshots与R1 replay states；每个committed step的`EngineStateDigestV1`必须相同。
- 从capture起点、每个周期checkpoint和任意合法state_seq开始replay，最终queue/batch/page/radix/request state均相同。
- R0 timeline与canonical event顺序/links一致；Chrome Trace派生后event count、flow endpoints与duration source可追溯。
- 三页面在相同cursor/filter下显示相同request state、step/batch和KV identity；UI显示值与query API golden JSON一致。
- v0.7 R0 capture可打开事件，不得出现R1控件；R2/R3 negative capability matrix必须一致。

### 8.2 Property/state invariants

- `state_seq_no`从checkpoint后严格连续+1；delta expected pre-digest等于当前digest，reduced post-digest等于记录值。
- canonical serialization与map/set插入顺序、Python process/hash seed无关；同一状态跨3次独立进程产生同一digest。
- checkpoint state本身满足v0.7 scheduler/KV/prefix/ownership不变量；reducer不得构造在线不允许的中间状态。
- critical delta缺失、重复、乱序、unknown breaking mutation或checksum错误时R1必须失败；不能跳过继续。
- 每个UI实体可追到bundle file/record ID；derived字段声明公式/source，estimated/unknown绝不标measured。
- timestamp移动时选择最大`commit_timestamp <= cursor`的state_seq；相同timestamp并列按state_seq，不按文件读取顺序。
- capture quotas有界；finalized manifest的文件size/checksum与实际一致；incomplete目录永不标complete。

### 8.3 Failure/stress matrix

| 场景 | 注入方式 | 必须结果 | 禁止结果 |
|---|---|---|---|
| missing critical delta | 删除中间state_seq | R1在gap处失败，R0已验证片段可看 | 跳过后声称digest成功 |
| duplicate/out-of-order delta | 重复或交换两条记录 | reader拒绝并报告seq/command | 依timestamp重排掩盖问题 |
| wrong post digest | 修改一个page valid count | 首次diff指向具体结构化path | 只报最终hash不同 |
| corrupt/truncated bundle | 修改checksum/截断zstd | quarantine/incomplete；最高能力降级 | 自动“修复”或执行未知内容 |
| exporter stall/disk quota | 阻塞writer/缩小bundle上限 | 推理继续；R1 capture停止并truncated | engine阻塞、磁盘无界增长 |
| UI hostile payload | 超大字段、路径穿越、HTML字符串 | size/path/schema校验或安全转义 | 任意文件读取/脚本执行 |
| old R0 capture | 打开v0.7 fixture | R0可用、R1禁用并解释缺checkpoint | 猜测state或错误升级 |
| viewer/reducer disagreement | 注入错误UI selector | golden view-model/E2E失败 | 三页面各自悄悄解释不同状态 |
| long capture | 达duration/bytes边界 | 原子finalize或明确incomplete，retention元数据存在 | silent truncation、损坏complete bundle |

## 9. Visualization Learning Story

### 9.1 本版本必须回答的问题

1. 一个请求从arrival到terminal经历哪些阶段、step、batch和KV变更？
2. 某个step谁被selected/deferred/preempted，recorded reason与budget快照是什么？
3. 当前cursor时request拥有哪些pages，复用了哪个radix extent，哪些lease阻止eviction？
4. 展示值来自measured event、derived reducer、estimated formula还是缺失/丢弃数据？
5. replay是否真的重建了控制面状态，首个不一致发生在哪里？

| Guided Request Story | request/model/stream events + reduced request state + static model graph | token/phase展开、跳step/batch/KV | event time measured；stage summary derived；未capture内容unknown |

## 10. Performance Hypothesis

### 10.1 本版本性能立场

验证观测开销边界，不优化Engine Core。metrics与sampled request trace应保持低扰动；完整engine-r1 capture是短时诊断模式，只要求有界并报告实际开销，不把其数据用于正式性能胜负比较。

### 10.2 Experiment card

```yaml
question: metrics与固定采样率request trace是否在target workload上保持可接受的全局开销
hypothesis: metrics相对off的output_token_throughput_tokens_per_second变化绝对值小于1%，预注册request采样率下小于3%；engine-r1虽更高但有界且不丢critical delta
primary_metric: relative_output_token_throughput_tokens_per_second_delta
guardrails: [correctness_pass_rate, server_ttft_request_weighted_p99, server_itl_token_weighted_p99, client_e2e_request_weighted_p99, peak_device_memory_bytes, request_failure_rate, telemetry_drop_rate, capture_bundle_bytes]
denominator: off/metrics/request profile 使用完全相同 offered arrival 集合；TTFT 分布只包含 accepted 且实际产生首个可交付 token 的请求；accepted 但在首 token 前 failed/cancelled 的请求不得伪造无限或零 TTFT，必须计入 `ttft_censored_before_first_token`、failure/outcome 计数并作为 SLO miss。E2E 按 accepted+terminal 分 outcome 报告；ITL 只包含至少两个输出 token 的 accepted 请求之相邻 token interval，并按 interval 加权。admission_rejected 单列且进入 offered-load/SLO 报告，不进入 accepted latency 分布；engine-r1 不参与正式胜负，只报告
```

## 11. Compatibility and Migration

### 11.1 Compatibility matrix

| Artifact | 读取上一版本 | 写入格式 | Breaking 条件 | 迁移/降级 |
|---|:---:|---|---|---|
| config | 是 | 新增capture/replay/UI quota字段 | 旧profile名称与R1能力混淆 | v0.7缺字段默认metrics/R0；R1需显式新配置 |
| public API/CLI | 是 | generation facade不变；新增replay/ui子命令 | `replay`静默能力降级 | capability不足始终fail closed，trace需显式选择 |
| event/capture | 是，v0.7 R0 | Bundle v1 + typed JSONL/JSON checkpoint | unknown major、delta/digest语义变化 | v0.7只R0；breaking需新reader/显式unsupported |
| model/weight manifest | 是 | 原digest进入bundle/view | digest改变导致错误跨run关联 | 作为不同run/model展示，不复用state/cache |
| cache/graph artifact | 不读取持久cache | checkpoint只含control metadata | 试图恢复K/V数据或在线运行 | 仅离线R1；不能用checkpoint启动engine |

### 11.2 Rollback

- 设置`capture.profile=request-r0`或`off`可关闭R1 delta/checkpoint；bundle必须准确写最高能力，UI隐藏state replay。
- UI不可用时仍交付CLI R0/R1与Chrome Trace/static HTML；这不改变capture事实或engine运行。
- 回退v0.7 binary不需要迁移在线state：先结束/标记当前capture、drain请求后重启。v0.8 bundle保持离线只读，v0.7工具只打开共同R0部分。
- schema reader升级失败时保留原bundle和checksums，不原地改写；迁移工具必须输出新目录、新manifest和provenance。

## 13. Known Limitations

- R1只重建控制面metadata，不保存K/V、logits或input token IDs，不能重执行模型或验证数值等价。
- R3 What-if不存在；UI只解释recorded DecisionRecord，不模拟新policy/cache结果。
- 三页面为离线单capture体验，没有生产live WebSocket、多人/远程capture管理或高级run diff。
- V0事件/checkpoint编码仍是typed JSONL/JSON；V1若冻结Protobuf需要显式migration/reader policy。
- engine-r1 capture是有扰动的短时诊断模式，不用于正式性能基线。
- 仍是单进程、单GPU、同步reference core；无OpenAI-compatible稳定服务、fast path或分布式能力。

### 13.1 下一版本输入

- v0.8 R0/R1 bundle、generated schema、三个view contracts和兼容策略成为v1.0稳定化输入。
- M7 Profile Gate只能消费v0.8 capture/metrics证据来选择最多一个分支；不得因“版本需要优化”绕过trigger。
- v1.0可在M8冻结stable event编码/服务接口，但必须提供v0.8 bundle读取或显式迁移/unsupported证据。
- R2/R3、高级GPU/Compare页面、live view仍需独立spec/trigger，不能从v0.8暗示为已实现。
